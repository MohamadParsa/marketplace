# راه‌حل فنی ساده و مرز ماژول‌ها

نسخه: ۱.۰ | تاریخ: ۲۰۲۶-۱۱-۱۷ | وضعیت: تحلیل و طراحی برای بازبینی تیم فنی | مالک بررسی: محصول و راهبر فنی؛ انتساب شخص هنوز انجام نشده

## راه‌حل پیشنهادی برای سرعت اجرا

یک monorepo و یک backend Go به صورت modular monolith؛ یک frontend React/TypeScript برای پنل مشترک و frontend مستقل سایت با SSR/SSG متناسب با SEO. PostgreSQL پیشنهاد مرجع داده، جست‌وجو و تراکنش است؛ انتخاب کتابخانه DB/ابزار migration با راهبر فنی. Redis از روز اول الزام نیست؛ ابتدا کش عمومی محدود و versioned و قفل مالی در دیتابیس. broker و microservice و موتور جست‌وجوی خارجی لازم نیستند.

این انتخاب‌ها راه‌حل پیشنهادی‌اند؛ دستور نصب یا تغییر ریپوی موجود نیستند. API، مدل و تسک‌ها به پوشه‌بندی خاص ریپو قفل نشده‌اند. تیم ابتدا قرارداد ماژول‌ها را تصویب و سپس ساختار موجود یا پروژه تازه را با آن تطبیق می‌دهد.

| ماژول | مالکیت | تماس مجاز |
| --- | --- | --- |
| Identity / Access | OTP، نشست، نقش، مجوز، محدوده فروشگاه | همه عملیات با principal معتبر |
| Catalog | دسته، خصوصیت، محصول، تنوع، عرضه، رسانه، برند | داده عمومی برای کشف؛ داده خصوصی فقط پنل |
| Pricing / Promotion | نرخ طلا، کمیسیون، روش فروش، مارکاپ، تخفیف و quote | محاسبه معتبر فقط سرور |
| Content | Page و Section، منو، لندینگ و محتوای footer | انتشار نسخه عمومی؛ بدون اجرای SQL/HTML آزاد |
| Checkout | سبد، quote، جلسه، رزرو و ارتباط با پرداخت | تراکنش رزرو و جلوگیری از خرید نامعتبر |
| Payment / Wallet | تلاش درگاه، دفتر مالی، شارژ، برداشت و refund | adapter بیرونی؛ مرجع نتیجه تأییدشده |
| Order / Shipping | خرید، اقلام، سفارش سلر، تأمین، مرسوله و حمل | اعمال وضعیت با guard و نسخه |
| Support / Settlement | پرونده، واگذاری، تخصیص و تسویه | اجرای مالی از Payment، بدون دستکاری balance |
| Notification / Audit | اعلان پس از رخداد قطعی و ردپا | خارج از مسیر بحرانی خرید؛ retry قابل پیگیری |

## مرز تراکنش و شکست

نوشتن دامنه، audit و رکورد رویداد لازم در یک تراکنش DB؛ تماس شبکه با درگاه داخل قفل طولانی DB انجام نشود. برای عملیات مالی، attempt پایدار ساخته، درخواست با کلید یکتا ارسال و نتیجه با compare-and-set نهایی شود. timeout به `unknown` تبدیل می‌شود؛ replay با همان کلید، نتیجه قبلی را می‌خواند. reconciliation با شناسه ارائه‌دهنده پیگیری می‌کند. outbox اختصاصی کوچک برای اعلان/اثر بیرونی کافی است؛ جدول تنظیمات عمومی محل outbox نیست.

```mermaid
flowchart LR
 A[سایت مشتری] --> API[API مشترک Go]
 B[پنل مشترک مدیر و سلر] --> API
 API --> G[کنترل مجوز و محدوده فروشگاه]
 G --> M[ماژول‌های دامنه]
 M --> DB[(PostgreSQL)]
 DB --> W[Worker اثر بیرونی و استعلام]
 W --> P[آداپتر نقدی / اعتباری / پیامک]
```

## قواعد غیرقابل واگذاری به frontend

مبلغ، درصد منتخب، موجودی قابل تخصیص، تعلق سفارش/عرضه، وضعیت پرداخت، سقف برداشت و مجوز مالی همگی سروری‌اند. frontend تنها شناسه‌ها، انتخاب‌ها و نسخه مورد انتظار را ارسال می‌کند. DTO عمومی، سلر، پشتیبانی و مالی جدا ساخته شوند؛ برگرداندن همه workspace و مخفی‌کردن UI برای سلر کافی نیست. مجوز مشاهده فرم از انتشار/تأیید/خروج وجه مستقل است.

## پیشنهاد ساده‌سازی

نقش و permission key رجیستری مشخص دارند؛ فرم‌ساز دلخواه مجوز تعریف نمی‌کند. خصوصیت کالا data-driven است ولی وضعیت سفارش و دفتر مالی schema و use case صریح دارند. با adapterهای `success/failure/unknown` همه مسیر پنل با داده آزمون بررسی شود؛ adapter آزمون در production روشن نشود. داده واقعی مشتری/کارت/توکن در fixture و لاگ ممنوع است.
