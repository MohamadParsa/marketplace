# اولویت اجرا، وابستگی و گیت تحویل

نسخه: ۱.۰ | تاریخ: ۲۰۲۶-۱۱-۱۷ | وضعیت: تحلیل و طراحی برای بازبینی تیم فنی | مالک بررسی: محصول و راهبر فنی؛ انتساب شخص هنوز انجام نشده

## اولویت با زمان انتشار یکی نیست

P0 زیربنا/صحت/امنیت یا مانع کار بعدی؛ P1 قابلیت لازم دامنه مورد درخواست؛ P2 توسعه پیشنهادی یا بهینه‌سازی قابل تأخیر. Wave ترتیب وابستگی را مشخص می‌کند؛ وجود P0 در موج آخر به معنی ساخت آن قبل از ماژول وابسته نیست. هیچ تاریخ یا نفرساعت قطعی تعهد نشده است.

| موج | خروجی قابل بررسی | گیت عبور |
| --- | --- | --- |
| W0 قرارداد و زیربنا | مدل، API، اسکلت پنل، واحد پول، error/version/idempotency، fixture و RBAC | راهبر فنی قرارداد را بپذیرد؛ CHQهای همان مسیر تعیین تکلیف؛ fixture فاقد داده واقعی |
| W1 کاتالوگ و تنظیمات پنل | دسته/برند/خصوصیت/محصول/عرضه، نرخ/روش/تخفیف و سکشن | فرم، خطا، permission و scope با API آزمون قابل بررسی؛ دامنه روشن کار می‌کند |
| W2 عملیات و مالی پنل با آزمون | سفارش، تأمین/حمل/پرونده، wallet/refund/settlement، unknown و audit | تست منفی سلر، هم‌زمانی و اثر یکتا؛ mock بدون انتقال واقعی؛ همه بخش‌های پنل قابل مرور |

## شروع پیشنهادی تیم

ابتدا CV-FND-01 تا CV-FND-05، CV-IAM-01 تا CV-IAM-04 و CV-CAT-01/02. بعد از قرارداد API، تیم پنل و backend روی منابع مستقل کار کنند. UI با fixture قراردادی سرعت می‌گیرد؛ fixture جای پذیرش backend نیست. تا آماده‌شدن سایت، سفارش‌های نمونه در محیط آزمون seed می‌شوند؛ پنل سفارش دستی واقعی به دامنه اضافه نشود.

تسک‌های طلا، تخفیف مرکب، جلسه وابسته به روش، انتقال واقعی پول و سیاست مجوز نامشخص محدودیت محلی دارند. در فایل هر تسک «بخش قابل شروع» و «مانع» آمده است؛ agent نباید برای سریع تمام‌کردن task پاسخ سؤال را بسازد. مسائل غیرمسدودکننده برای فرم/DTO با حالت غیرفعال و دلیل روشن پیاده شوند و قابلیت عملیاتی غلط نشان داده نشود.

## شرط Done برای یک تسک

دامنه و قرارداد رعایت شده؛ خروجی مشخص؛ تست معنی‌دار سناریوی اصلی و خطر همان تغییر؛ مجوز/مالکیت و حالت‌های خطا مرتبط؛ snapshot و هم‌زمانی مالی در صورت ارتباط؛ سند/API به‌روز؛ شاهد آزمون و محدودیت ثبت؛ بازبینی تیم. mock success، build موفق و HTTP 200 به‌تنهایی قبول قابلیت مالی یا provider نیستند. برای یک تغییر ظاهری کم‌خطر تست تقلیدی لازم نیست؛ بررسی بصری متناسب کافی است.

## گیت انتشار کل دامنه

همه قابلیت‌های P1 درخواست‌شده یا تحویل شده باشند یا تعویقشان صریحاً توسط مالک ثبت شود؛ P1 را بدون تصمیم به «بعداً» تبدیل نکنید. انتخاب مسیر بصری/سیاست انتشار محتوای کاربران، مجوزها و قراردادها باید همان بخش را آزاد کند. هیچ داده/پول واقعی برای دورزدن نبود sandbox استفاده نشود. مهاجرت/rollout و rollback با شاهد مستقل؛ پشتیبانی روش پیگیری unknown را بلد باشد.

تخمین تسک در kickoff با افراد واقعی و ظرفیت واقعی جایگزین S/M شود. اگر یک task بیش از دو روز واقعی شد، با حفظ شناسه مادر و پذیرش‌ها به دو خروجی قابل بازبینی تقسیم شود؛ کار نامعلوم را با تخمین صفر پنهان نکنید.
