# قرارداد اجرای تسک توسط تیم فنی و AI agent

نسخه: ۱.۰ | تاریخ: ۲۰۲۶-۱۱-۱۷ | وضعیت: تحلیل و طراحی برای بازبینی تیم فنی | مالک بررسی: محصول و راهبر فنی؛ انتساب شخص هنوز انجام نشده

## ترتیب کار روی هر تسک

فایل همان تسک، سند تحلیل مرتبط، قرارداد API و سؤال‌های مانع را بخوانید. scope، dependency و permission را استخراج کنید. ابتدا خروجی قابل بازبینی کوچک بسازید، سپس تست‌های مرتبط و گزارش تحویل. در بخش مبهم مالی/امنیتی/رفتاری حدس نزنید؛ مانع را دقیق ثبت و بخش مستقل روشن را ادامه دهید. تولید فایل و build موفق به‌تنهایی تکمیل فلو نیست.

راه‌حل فنی این بسته پیشنهادی است؛ تغییر ابزار یا پوشه‌بندی با دلیل کوتاه مجاز است، تغییر قاعده بیزینسی بدون ثبت پاسخ مالک مجاز نیست. نیازمندی‌های تاییدشده کارت/PDP/مارکاپ/پنل مشترک را از روی ریپوی قدیمی برنگردانید. در پروژه مقصد، AGENTS و قواعد امنیت/گیت/تست همان پروژه نیز رعایت شوند؛ این بسته خود مجوز deploy یا انتقال پول نیست.

## ورودی حداقلی یک اجرای agent

```text
تسک: CV-...؛ فقط همین scope.
مسیر پروژه مقصد: توسط تیم تعیین شود؛ D:\Cherriva در تهیه بسته تغییر نکرده است.
قرارداد مبنا: نسخه ۱.۰ این بسته + پاسخ‌های ثبت‌شده بعدی.
وابستگی‌های انجام‌شده با شاهد: ...
سؤال‌های حل‌شده/مانع همین مسیر: ...
خروجی: کد محدود + تست معنادار + تغییر قرارداد/سند لازم + گزارش محدودیت.
```

## گزارش خروجی

شناسه تسک، فایل‌های تغییرکرده، رفتار قبل/بعد، schema/API مؤثر، مجوز/محدوده، تست و داده، نتیجه، مانع و کار باقی‌مانده. وضعیت‌ها: `todo`، `in-progress`، `blocked-part`، `review`، `done` با شاهد. اجرای mock، unit/integration، مرورگر و sandbox/provider واقعی جدا گزارش شوند. برای پاسخ unknown از کد `failed` و برای mock success از «پرداخت واقعی موفق» استفاده نشود.

تخمین‌ها نسبی‌اند و انتساب اشخاص/موعد در kickoff ثبت می‌شود. agent خودش مسئول انسانی/تأییدکننده نهایی/پاسخ CHQ را نسازد. ادغام، push و انتشار تابع اجازه تیم در task واقعی است. هیچ تسک این بسته خودکار شروع یا زمان‌بندی نشده است.

برای تسک‌های تراکنشی، [گذار وضعیت‌ها و قیدهای هم‌زمانی](18-state-transitions.md) هم جزو ورودی کار است.
