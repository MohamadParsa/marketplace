# هویت واحد، موبایل، ایمیل و رمز

شناسه: CV-R2-IAM | نسخه: ۱.۱ | تاریخ: ۲۰۲۶-۱۱-۱۷ | وضعیت: قواعد اعلام‌شده + طراحی فنی پیشنهادی در بازبینی | مالک تصمیم: الیاس

## قاعده بیزینسی اعلام‌شده

یک `User` همان شخص است؛ خریدکردن، کار در بک‌آفیس و عضویت در یک یا چند فروشگاه کاربردهای همان هویت‌اند. حساب مشتری یا ادمین/سلر جدا ساخته نمی‌شود. فروشگاه همچنان موجودیت جداست؛ یک کاربر با فروشگاه برابر نیست. نام/موبایل گیرنده سفارش نیز می‌تواند با صاحب حساب متفاوت باشد.

ورود نخست با شماره تلفن است. کاربر از پروفایل می‌تواند ایمیل اضافه و یک رمز تعریف کند. در ورود بعدی، موبایل+رمز یا ایمیل+همان رمز پذیرفته می‌شود. این تصمیم الزام حذف OTP بعد از ثبت رمز ایجاد نمی‌کند؛ در طرح، مسیر موبایل/OTP نیز باقی مانده است. امکان حذف یا اجبار OTP در آینده جداگانه بررسی شود.

## طراحی داده پیشنهادی

- `User(id, display_name, normalized_mobile, mobile_verified_at, normalized_email?, email_verified_at?, state, version)`؛ موبایلِ ورود نخست، نرمال‌شده و تأییدشده و یکتا؛ ایمیل اختیاری است و یکتایی/تأیید آن طبق سیاست انتخاب‌شده کنترل شود.
- `PasswordCredential(user_id UNIQUE, password_hash, changed_at, version)`؛ یک credential برای همه identifierهای همان کاربر. رمز متن‌خام در User، audit، log یا پاسخ API وجود ندارد. انتخاب نهایی الگوریتم/پارامتر hash با مسئول امنیت/فنی؛ در این سند dependency نصب نمی‌شود.
- `StoreMembership(user_id, store_id, state)` و `RoleGrant(user_id, role_id, scope)` به همان User متصل‌اند. خرید معمولی نیازمند نقش مدیریتی نیست. جمع نقش‌ها نباید محدوده دو فروشگاه را مخلوط یا اختیار جهانی ایجاد کند.
- سفارش `buyer_user_id`، کیف پول `owner_user_id` و نشانی `owner_user_id` دارند. اگر برای راحتی خواندن `CustomerProfile` وجود داشته باشد، وابسته ۱به۱ به User است و هویت یا رمز مستقل ندارد.

ایمیلِ تایپ‌شده نباید حساب دیگری را خودکار ادغام کند. پیشنهاد طراحی: تأیید مالکیت ایمیل و یکتایی normalized پیش از استفاده برای ورود؛ این مرحله پیشنهاد امنیت/صحت داده است، جزئیات آن هنوز مصوبه جداگانه نیست. اصلاح شماره یا credential حساس، احراز مجدد و ابطال نشست‌های لازم می‌خواهد؛ سیاست نهایی در بازبینی امنیت تکمیل شود.

## فلو و قرارداد پیشنهادی

1. موبایل → OTP challenge → تأیید → ایجاد/یافتن همان User → نشست و مجوزهای معتبر.
2. پروفایل → ثبت ایمیل pending → challenge مالکیت → تأیید و اتصال به همان User.
3. پروفایل → ثبت/تغییر رمز → hash سمت سرور → حذف متن خام از حافظه درخواست و audit بدون secret.
4. `POST /v1/auth/password-login { identifier, password }` → resolve identifier تأییدشده → همان User → نشست. identifier نوع حساب/نقش را تعیین نمی‌کند.
5. `GET/PATCH /v1/me`، `POST /v1/me/email-challenges`، `POST /v1/me/email-verifications`، `PUT /v1/me/password` به عنوان route پیشنهادی؛ با قرارداد API تیم نهایی شوند.

پیام ناموفق عمومی، rate limit برای هر دو روش و جلوگیری از account enumeration لازم است. قواعد OTP منتقل‌شده در بسته ۱.۰ به جای خود باقی‌اند؛ افزودن رمز مجوز حذف کنترل تلاش و امنیت نشست نیست. تغییر email/password نباید سفارش، کیف پول یا عضویت جدید بسازد.
