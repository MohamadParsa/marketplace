# اجرای محلی چریوا — Windows / D:\Cherriva

[تنظیمات فعلی درگاه‌ها برای بررسی مالک](delivery/gateway-currency-and-switches-2026-11-28.md): «تنظیمات خرید و حمل ← پرداخت و مقصد وجه ← بازکردن درگاه ← سوییچ/ویرایش تنظیمات». همه بخش‌ها در شروع بسته‌اند و افزودن درگاه وجود ندارد. راه‌انداز، کلید رمزنگاری محلی را بیرون مخزن نگه می‌دارد؛ credential هر درگاه در تنظیمات همان درگاه ذخیره می‌شود. callback و شرح تراکنش ورودی تنظیمات نیستند؛ origin محلی از `PAYMENT_PUBLIC_BASE_URL` و مسیر از کد می‌آید. اجرای پرداخت هنوز قدم بعد است.

بازبینی جاری بک‌آفیس: سرمنوها در ورود اول بسته‌اند؛ نظر و پرسش زیر «کاتالوگ» هستند. تنظیم خصوصیات دسته چهار زون و ترتیب مستقل دارد؛ قیمت و موجودی هر عرضه از یک مودال ذخیره می‌شوند و SKU دستی لازم نیست. در تنظیمات حمل، روزهای کاری سایت را انتخاب کنید؛ تقویم فروشگاه همچنان مستقل/قابل ارث‌بری است. [هفت تسک، شواهد و توضیح صفحهٔ قیمت/کمیسیون](delivery/backoffice-refinement-2026-11-25/backoffice-review-2026-11-27.md).

فهرست فعال کشور،۳۱استان و۱۴۸۱شهر، در دیتابیس بررسی محلی وارد شده است. مدیریت از «تنظیمات خرید و حمل ← استان‌ها و شهرها» و انتخاب مقصد از فرم آدرس سایت در دسترس است. [منبع و راهنمای ورود روی محیط دیگر](../data/iran-geography/README.md) · [گزارش۲۰۲۶-۱۱-۲۷](delivery/iran-geography-import-2026-11-27.md).

انتساب حمل، پیش‌نویس اختصاصی و بررسی نسخه در تب «روش‌های حمل» همان فروشگاه در `/stores?store=<id>&tab=shipping` است. ادمین از ردیف هر روش در `/shipping` با «تنظیم فروشگاه‌ها» محدودهٔ یک/همه را انتخاب می‌کند. عضو در «فروشگاه‌های من» (`/my-stores`) فقط تنظیمات حمل/تقویم مجاز خودش را می‌بیند. منوی مستقل قبلی حذف و `/store-shipping` به مسیر جدید هدایت می‌شود. [راهنما و شواهد جاری](delivery/backoffice-refinement-2026-11-25/store-shipping-integration-2026-11-27.md) · [مجوزهای #122](delivery/shipping-refinement-2026-11-26/issue-122-verification.md).

مدیریت روش عمومی حمل در منوی «روش‌های حمل» و `/shipping` است؛ فرم، فیلتر، صفحه‌بندی و ویرایش هر روش جدا هستند. پیش‌کرایه/پس‌کرایه و پوشش شناسه‌ای شهر/دسته از این صفحه ثبت می‌شوند. تنظیمات خرید پیوند همین صفحه و تقویم عمومی/ساعت آماده‌سازی را دارد. [شواهد #121 و مرز ظرفیت/برنامه](delivery/shipping-refinement-2026-11-26/issue-121-verification.md).

تنظیم وقفه و تقویم فروشگاه از منوی «وقفه و تقویم فروشگاه» در `/store-preparation` در بک‌آفیس و پنل فروشنده در دسترس است. برای اعضای فروشگاه، مدیر باید مجوزهای مشاهده و ویرایش همان فروشگاه را در نقش فروشگاه تعیین کند. روزهای تعطیل، تاریخ‌های عمومی، واحد مدت حمل و ساعت‌های اولیه از تنظیمات خرید و حمل مدیریت می‌شوند. به‌روزرسانی: ۲۰۲۶-۱۱-۲۳. سورس کامل از [PR #38](https://github.com/MohamadParsa/marketplace/pull/38) در شاخه `main` موجود است؛ [کامیت ادغام سورس](https://github.com/MohamadParsa/marketplace/commit/3163d1702f2396d8d1818d12c7bf92bcab9a35bf). این راهنما اجرای بررسی محلی با PostgreSQL پایدار را توضیح می‌دهد.

## اجرای سریع روی سیستم فعلی الیاس

در PowerShell:

```powershell
Set-Location D:\Cherriva
.\Start-Cherriva.cmd
```

راه‌انداز وابستگی‌های دو frontend را با `npm ci` نصب می‌کند، هر دو را build می‌کند، Go API را می‌سازد و سایت و بک‌آفیس را اجرا می‌کند. PostgreSQL خصوصی نسخه بررسی همین سیستم نیز در صورت توقف راه‌اندازی می‌شود. اولین اجرا به اینترنت برای دریافت dependencyها نیاز دارد.

اگر frontendها از قبل با سورس فعلی build شده‌اند:

```powershell
Set-Location D:\Cherriva
powershell -NoProfile -ExecutionPolicy Bypass -File .\Start-Cherriva.ps1 -NoBuild
```

پس از تغییر React یا دریافت نسخه جدید، اجرای کامل را انجام دهید؛ `-NoBuild` فقط build frontend را رد می‌کند و می‌تواند رابط قدیمی نشان دهد.

ساختن frontend به‌تنهایی API در حال اجرا را تازه نمی‌کند. اگر رابط جدید کنار executable قدیمی قرار بگیرد، مسیر تازه ممکن است۴۰۴ بدهد یا پاسخ تنظیمات فیلدهای لازم را نداشته باشد. برای ارتقای اجرای محلی، build رابط و restart API باید از یک نسخه سورس باشند؛ در نسخهٔ جاری این خطا پیام قابل بازیابی دارد و پنل سفید نمی‌شود. [بازتولید و اصلاح۸۰۹۸](delivery/shipping-refinement-2026-11-26/issue-121-verification.md#local-runtime-recovery).

در آزمونِ سرویس جدا، خروجی frontend را نیز در مسیر جدا بسازید و `WEB_ROOT` همان سرویس را به آن بدهید؛ استفاده از `apps/backoffice-web/build` مشترک، رابط اجرای اصلی را پیش از ارتقای API آن عوض می‌کند. نمونهٔ خروجی آزمون از پوشهٔ `apps/backoffice-web`: `npm run build -- --outDir ../api/tmp/shipping-review/web`؛ پوشهٔ `tmp` وارد Git نمی‌شود.

| محیط | آدرس |
| --- | --- |
| سایت | http://localhost:5197 |
| بک‌آفیس | http://localhost:8098 |
| ورود فروشنده در پنل مشترک | http://localhost:8098/seller-login |

[حساب ادمین و رمز مشترک تیم](delivery/local-review-access.md) در دیتابیس بررسی همین سیستم موجود است. برای مشاهده تغییرات، مرورگر را refresh کنید و در صورت نیاز دوباره وارد شوید؛ نشست ورود پس از restart قابل اتکا نیست.

## راه‌اندازی روی سیستم دیگر، از جمله سیستم پارسا

پیش‌نیازها: Git، Go سازگار با `apps/api/go.mod` (حداقل 1.23)، Node.js/npm و PostgreSQL. این تحویل محلی با Node 24 و PostgreSQL 17 بررسی شده است. راه‌انداز Windows است و روی سیستم دیگر PostgreSQL را دانلود یا نصب نمی‌کند.

اگر پوشه پروژه هنوز وجود ندارد:

```powershell
git clone https://github.com/MohamadParsa/marketplace.git D:\Cherriva
Set-Location D:\Cherriva
```

اگر clone موجود است، ابتدا تغییرات محلی را بررسی کنید و سپس از شاخه `main` نسخه تازه بگیرید:

```powershell
Set-Location D:\Cherriva
git status
git switch main
git pull --ff-only
```

در PostgreSQL یک دیتابیس اختصاصی بررسی با کاربر دارای مجوز ایجاد جدول بسازید. در همان PowerShell، آدرس اتصال دیتابیس خود را جایگزین مقدار نمونه کنید؛ اطلاعات اتصال را commit نکنید:

```powershell
$env:REVIEW_DATABASE_URL = 'postgres://REVIEW_USER:REVIEW_PASSWORD@127.0.0.1:5432/cherriva_review?sslmode=disable'
Remove-Item Env:DATABASE_URL -ErrorAction SilentlyContinue
.\Start-Cherriva.cmd
```

متغیر اتصال باید در همان نشست تنظیم شود؛ راه‌انداز فایل `.env` را بارگذاری نمی‌کند. راه‌انداز ریشه پروژه migrationهای نسخه بررسی را پیش از شروع API اعمال می‌کند و داده در PostgreSQL باقی می‌ماند. `DATABASE_URL` اتصال محیط عمومی است و نباید همراه حالت آزمون تنظیم شود.

حساب مشترک الیاس روی دیتابیس تازه خودکار ساخته نمی‌شود. مدیر ساختگی دیتابیس بررسی تازه `09000000001` است: با شماره موبایل وارد شوید و کد OTP آزمون نمایش‌داده‌شده در فرم را وارد کنید. این کد فقط برای اجرای loopback و `APP_ENV=test` است. راه‌انداز، ارسال پیامک واقعی را غیرفعال می‌کند؛ داده بررسی جای داده عملیاتی نیست.

## داده نمونه تنوع و بررسی خرید

پس از روشن‌شدن بک‌آفیس، از ریشه پروژه می‌توان سه محصول ساختگی دارای محور رنگ/گارانتی و دو فروشنده را ساخت:

```powershell
node .\tests\e2e\seed-variant-showcase.cjs
```

اسکریپت فقط API محلی دارای OTP آزمون را می‌پذیرد و URL محصولات همین دیتابیس را چاپ می‌کند. یک ترکیب ناموجود نیز برای بررسی PDP دارد. اطلاعات استان/شهر و ارسال نمونه از داده بررسی‌اند؛ فهرست کامل جغرافیایی کشور نیستند. مدیریت استان/شهر و روش‌های ارسال از تنظیمات خرید در بک‌آفیس انجام می‌شود.

برای مرور اصلاحات: PDP ← افزودن/تغییر تعداد ← سبد ← مرحله آدرس و ارسال ← مرحله پرداخت؛ سپس جزئیات سفارش و واریز را در بک‌آفیس بررسی کنید. [گزارش، سناریوها و تصاویر](delivery/initial-launch/purchase-refinements-verification.md) مرجع جزئیات است. ارسال فعلی بازه حداقل/حداکثر روز دارد؛ اسلات ظرفیت‌دار در #16 باقی مانده است.

## خطاهای رایج و اطلاعات اجرا

- `go` یا `npm` پیدا نمی‌شود: نصب و PATH را بررسی و PowerShell جدید باز کنید.
- اتصال دیتابیس شکست می‌خورد: PostgreSQL، نام دیتابیس و `REVIEW_DATABASE_URL` را بررسی کنید. روی سیستم دیگر runtime خصوصی الیاس وجود ندارد.
- پورت 8098 یا 5197 اشغال است: راه‌انداز فقط API متعلق به runtime خودش را متوقف می‌کند؛ برنامه دیگر را خودتان بررسی کنید.
- رابط قدیمی است یا فایل build پیدا نمی‌شود: راه‌انداز را بدون `-NoBuild` اجرا کنید.
- روش ارسال برای آدرس نیست: فعال‌بودن استان/شهر و پوشش روش ارسال همان فروشنده را در پنل بررسی کنید.

لاگ‌ها و فایل اجرایی در `%USERPROFILE%\.codex\local-runtimes\cherriva` هستند؛ از جمله `backoffice.err.log` و `storefront.err.log`. فرآیندهای API در پس‌زمینه اجرا می‌شوند و بستن پنجره راه‌انداز آن‌ها را متوقف نمی‌کند. اجرای دوباره راه‌انداز، APIهای متعلق به خودش را جایگزین می‌کند.

این تحویل روی Liara منتشر نشده است؛ انتشار عمومی با پارسا و گیت باز #12 است. [راهنمای استقرار](delivery/liara-deployment.md) · [تطبیق کامیت سورس و مستندات](delivery/source-document-map.md).

## Redis و warmup کاتالوگ عمومی — #41

روی سیستم فعلی Redis۷ در WSL موجود است. راه‌انداز، در نبود `REDIS_URL`، [اسکریپت محلی](../scripts/start-review-redis.sh) را اجرا می‌کند: loopback، پورت اختصاصی۵۶۳۷۹، سقف۱۲۸MiB، allkeys-lru و بدون ذخیره دیسکی کش. اگر WSL/Redis موجود نباشد، warning می‌دهد و برنامه از PostgreSQL اجرا می‌شود؛ روی سیستم دیگر می‌توان یک Redis خصوصی آماده را از طریق env داد. secret/اتصال در Git ثبت نشود.

| تنظیم محیط | رفتار |
| --- | --- |
| `PUBLIC_CACHE_ENABLED=true` و `REDIS_URL` خصوصی | کش JSON عمومی فعال؛ در اجرای دستی/سرور باید صریحاً تنظیم شوند. |
| `CACHE_WARMUP_ENABLED=false` | فقط warmer خاموش؛ پیش‌فرض true است. |
| `CACHE_HOME_TTL_SECONDS` | ۱تا۳۰۰؛ پیش‌فرض۳۰۰. |
| `CACHE_PRODUCT_TTL_SECONDS` | ۱تا۶۰۰؛ پیش‌فرض۶۰۰. |
| `CACHE_LISTING_TTL_SECONDS` | ۱تا۶۰؛ پیش‌فرض۶۰. |
| `CACHE_SUGGESTIONS_TTL_SECONDS` | ۱تا۳۰؛ پیش‌فرض۳۰. |

مقدار نامعتبر/بیش از سقف به پیش‌فرض برمی‌گردد. در هر startup سایت، خانه/بنر و۴PLP و حداکثر۱۰۰PDP اولویت‌دار با۲worker و۴۵ثانیه آماده می‌شوند؛ همه PDPها و باینری‌ها یکجا preload نمی‌شوند. warmer در پس‌زمینه است؛ خراب‌شدن Redis سایت را از دسترس خارج نمی‌کند. cache hit نسخه جاری را از PostgreSQL بررسی می‌کند؛ بعد از ویرایش قیمت/موجودی منتظر TTL نمی‌ماند.

```powershell
.\Start-Cherriva.ps1 -NoBuild -NoCache
# اگر در همان PowerShell دوباره کش می‌خواهید:
$env:PUBLIC_CACHE_ENABLED = 'true'
.\Start-Cherriva.ps1 -NoBuild
```

migrationهای۰۰۰۰۰۵و۰۰۰۰۰۶، نمای عمومی و نسخه‌های پایدار را اضافه می‌کنند و حتی بدون Redis نیز پیش‌نیاز همین سورس‌اند؛ راه‌انداز قبل از اجرا آن‌ها را اعمال می‌کند. سبد/مالی/OTP/نشست/پنل خصوصی در Redis نیستند. `public cache warmup` و سپس شمارنده‌های عمومی هر دقیقه در لاگ سرور دیده می‌شوند؛ اتصال یا اطلاعات کاربر در گزارش cache چاپ نمی‌شود. [گزارش، سرعت، تصاویر و محدودیت‌ها](delivery/storefront-followups/issue-41-verification.md).

## آدرس و نقشه — #100/#101

پروفایل مشتری کد ملی دارد؛ تحویل به خود مشتری نیازمند تکمیل نام/کد ملی است. آدرس قدیمی محفوظ است و پیش از خرید تازه باید پلاک/گیرنده‌اش تکمیل شود. مهاجرت۱۱ از طریق همان راه‌انداز اجرا می‌شود. فعلاً مالک اتصال آماده نقشه را انتخاب کرده و کلیدها بعداً تنظیم می‌شوند؛ فرم دستی بدون کلید فعال است. `NESHAN_WEB_KEY` از نوع وب و محدود به دامنه و `NESHAN_SERVICE_KEY` فقط خصوصی سرور است؛ کلیدها در Git و کلید سرویس در `VITE_*` نباشند. [تنظیمات، سقف درخواست و گام آزمون واقعی](architecture/contracts/customer-address-map.md).

راه‌انداز هنگام استفاده از cluster خصوصی موجود، پورت واقعی آن را از فایل وضعیت همان cluster می‌خواند؛ تغییر پورت محلی از۵۵۴۳۷ به۵۴۳۲ دیگر باعث اتصال به پورت اشتباه نمی‌شود. تنظیم صریح `REVIEW_DATABASE_URL` همچنان بر این کشف محلی مقدم است.


پس از تحویل #107/#108، منوی «کاتالوگ» صفحات `/categories`، `/attributes`، `/brands` و `/products` را باز می‌کند؛ چهار ریل خانه در `/home-settings` و بخش محتوا هستند. `/home-catalog` فقط لینک‌های قدیمی را به مقصد جدید هدایت می‌کند. [گزارش و تصاویر](delivery/backoffice-refinement-2026-11-25/issues-107-108-verification.md).

## بررسی برنامه و ظرفیت حمل — #16

در «روش‌های حمل» برای روش اسلات‌دار، ساعت شروع/پایان ۲۴ساعته HH:mm دلخواه تعریف، به روزها منتسب و ظرفیت هر بازه و سقف روز را صریح وارد کنید؛ کپی برنامهٔ یک روز به چند روز ممکن است. در تب «روش‌های حمل» فروشگاه، عمومی را بپذیرید یا برنامهٔ اختصاصی را با همان چرخهٔ draft/review منتشر کنید. «ظرفیت روز» مصرف/رزرو/باقیمانده و پیش‌نمایش شش تاریخ را نشان می‌دهد؛ ورودی تاریخ شمسی است. روش قدیمی بدون سقف صریح در خرید تازه ارائه نمی‌شود؛ اعداد نمونه ظرفیت واقعی نیستند. دستور `npm run test:shipping-dates` تبدیل شمسی/مرز تهران را بررسی می‌کند.

## بررسی صف تأخیر تأمین — #10

در سفارش‌ها (`/orders`) صف تأخیر تأمین برای ادمین دارای `commerce.orders.read` نمایش داده می‌شود؛ فروشنده در `/commerce` فقط صف و سفارش‌های مجاز خودش را می‌بیند. صف از موعد snapshot پرداخت قطعی استفاده می‌کند و در صفحهٔ باز هر۶۰ثانیه تازه می‌شود. جست‌وجوی شماره/فروشگاه، بررسی فوری و پیوند جزئیات/پرونده موجودند. نبود مهلت تاریخی جدا مشخص است؛ بررسی این صف عملیات مالی یا تغییر خودکار سفارش ندارد. [شاهد](delivery/shipping-refinement-2026-11-26/issue-10-verification.md).

ضریب تبدیل در تنظیمات پرداخت درگاه، ضریب ضرب مبلغ سایت است: مبلغ تومان ×۱۰ = مبلغ ریال؛ برای درگاه تومانی ×۱. واحد و ضریب با ذخیره در پنل تغییر می‌کنند و داده مالی گذشته بازنویسی نمی‌شود.
