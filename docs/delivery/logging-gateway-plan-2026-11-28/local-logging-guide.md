# راهنمای لاگ محلی و گزارش ادمین

این راهنما مربوط به اجرای #155/#156/#157 و #75/#76/#77 است؛ [وضعیت و شواهد](execution.md) و [ماتریس پوشش](coverage.md) مرز اجرا را مشخص می‌کنند. اتصال درگاه و احراز پذیرنده #158..163 همچنان معوق‌اند.

## مشاهده در بک‌آفیس

با حساب ادمین از «گزارش و اطلاع‌رسانی ← گزارش فعالیت‌ها» یا `/reports` وارد شوید. سه تب دارید:

1. **سابقه عملیات:** حسابرسی دیتابیس، عامل، هدف، زمان شمسی، نتیجه و تغییرات مجاز قبل/بعد. شرح خصوصی در فرم/پرونده اصلی نگهداری می‌شود؛ مقدار credential نمایش داده نمی‌شود.
2. **لاگ اجرا و سرویس‌ها:** نوع، شدت، نتیجه، زمان و شناسه پیگیری؛ فیلتر نوع/نتیجه/عامل/رویداد/operation و بازه شمسی. «نمایش بیشتر» صفحه بعد را می‌گیرد؛ فیلترهای جدول در ابتدا بسته‌اند.
3. **رفتار مشتری و مسیر خرید:** شمار رخدادهای موفق مشاهده، جست‌وجو، افزودن سبد، quote، ثبت سفارش و پرداخت قطعی، با فیلتر تاریخ/دستگاه/دسته/محیط. داده آزمون با production ترکیب نمی‌شود.

هم API و هم صفحه فقط برای ادمین بک‌آفیس مجازند؛ پنهان‌کردن منو جای کنترل سرور را نمی‌گیرد. CLI و فایل محلی تحت دسترسی حساب سیستم‌عامل اجراکننده و مدیر همان دستگاه‌اند؛ مجوز نقش‌های وب به دسترسی مستقیم فایل سیستم تعمیم داده نمی‌شود.

بالای گزارش، وضعیت مقصد، تعداد ثبت‌شده، افت صف و خطای نوشتن دیده می‌شود. این شمارنده‌ها متعلق به همان پردازه و از زمان راه‌اندازی آن هستند؛ با restart صفر می‌شوند. `written` یعنی نوشتن انجام شده و به معنی حفظ دائمی پس از retention نیست. در دو پردازه سایت و بک‌آفیس، فایل‌ها مشترک ولی شمارنده‌های هر پردازه جدا هستند. دریافت آمار توسط API، خود ممکن است رویداد جدید تولید کند؛ مقایسهٔ دقیق شمارنده‌ها نیازمند درنظرگرفتن این تأخیر است.

## تنظیمات اجرای سرور

متغیرها را پیش از اجرای API یا `Start-Cherriva.ps1` تنظیم و پردازه‌ها را دوباره راه‌اندازی کنید؛ تغییر این متغیرها build محصول نمی‌خواهد. مسیر را خارج از web-root و مخزن و روی دیسک خصوصی حساب سرویس نگه دارید؛ آن را share عمومی نکنید. قرارگیری داخل web-root پیکربندی ناامن محسوب و راه‌اندازی رد می‌شود؛ خطای دسترسی/نوشتن فایل مقصد به حالت storage-unavailable می‌رود و خرید را متوقف نمی‌کند. در Windows مسیر پیش‌فرض `%LOCALAPPDATA%\Cherriva\operation-logs` و در سایر محیط‌ها `os.UserCacheDir()/Cherriva/operation-logs` است.

| متغیر | پیش‌فرض | معنا |
| --- | --- | --- |
| `OPERATION_LOG_DIR` | مسیر بالا | پوشه خصوصی JSON Lines؛ مسیر و ancestorهای symlink/junction برای منع قرارگیری داخل web-root بررسی می‌شوند. |
| `LOG_RETENTION_DAYS` | `7` | حداکثر عمر فایل فنی، integration، security و business |
| `LOG_BEHAVIOR_RETENTION_DAYS` | `30` | حداکثر عمر فایل رفتار مشتری و correlation خصوصی quote |
| `LOG_MAX_MB` | `500` | سقف مشترک فایل‌های لاگ شناخته‌شده، برحسب MiB |
| `LOG_FILE_MB` | `8` | حد چرخش هر فایل، برحسب MiB؛ از سقف مشترک بزرگ‌تر نباشد. |
| `LOG_QUEUE_SIZE` | `1024` | اندازه صف حافظه؛ کران مجاز۱تا۶۵۵۳۶ |

مقادیر خالی/نامعتبر عددی به پیش‌فرض برمی‌گردند؛ پیکربندی ناسازگار مقصد در آمار با `storage-unavailable` مشخص می‌شود. نگهداری بر اساس زمان فایل است؛ گردش روزانه/حجم و پاکسازی هنگام نوشتن و هر دقیقه انجام می‌شوند. سقف حجم می‌تواند فایل‌های قدیمی را **پیش از پایان مدت** حذف کند. فایل هر instance/type/day جدا و نوشتن/پاکسازی با قفل بین پردازه‌ای هماهنگ است. فایل‌های ناشناخته و audit دیتابیس در این پاکسازی حذف نمی‌شوند. حذف نامحدود/قانونی سابقه، تضمین بدون افت یا بایگانی دائمی وعده این مقصد نیست.

نمونهٔ محلی در PowerShell:

```powershell
$env:OPERATION_LOG_DIR = Join-Path $env:LOCALAPPDATA 'Cherriva/operation-logs'
$env:LOG_RETENTION_DAYS = '7'
$env:LOG_BEHAVIOR_RETENTION_DAYS = '30'
$env:LOG_MAX_MB = '500'
.\Start-Cherriva.ps1 -NoBuild
```

هیچ secret یا credential در متغیرهای نمونه وجود ندارد. برای تغییر مقصد آینده، adapter جدید `operationlog.Sink`/`Scanner` به runtime متصل می‌شود؛ نقاط ثبت دامنه وابسته به فایل، Elastic یا ClickHouse نیستند.

## جست‌وجوی محلی فقط‌خواندنی

از ریشه مخزن، با حساب سیستم‌عامل مجاز:

```powershell
$taskLogDir = Join-Path $env:LOCALAPPDATA 'Cherriva/operation-logs'
go -C apps/api run ./cmd/log-query -dir $taskLogDir -type technical -outcome rejected -limit 50
go -C apps/api run ./cmd/log-query -dir $taskLogDir -operation 0123456789abcdef0123456789abcdef -from '2026-11-28T00:00:00+03:30' -to '2026-11-28T23:59:59+03:30'
go -C apps/api run ./cmd/log-query -dir $taskLogDir -event checkout.preview -severity warn -limit 50
```

شناسهٔ مثال ساختگی است؛ مقدار واقعی را از `X-Operation-ID` پاسخ یا جزئیات گزارش بگیرید. برای صفحه بعد، `next_cursor` پاسخ را به `-cursor` بدهید؛ حداکثر۲۰۰رویداد در صفحه است. خروجی JSON پالایش‌شده است و CLI چیزی در پوشه لاگ نمی‌نویسد. زمان فایل UTC و زمان گزارش تهران است؛ تاریخ فرم شمسی است و ذخیره/فیلتر به timestamp واقعی تبدیل می‌شود.

`request_id` برای هر درخواست سرور تازه است. `operation_id` می‌تواند مراحل یک عملیات را مرتبط کند؛ از آن برای مجوز، اثبات پرداخت یا هویت کاربر استفاده نکنید. ورودی `X-Operation-ID` فقط قالب محدود می‌پذیرد. بازیگر از احراز سرور است و subject رفتار، مشتری سفارش؛ پرداخت با تأیید ادمین همچنان به مشتری و دستگاه آغاز خرید مربوط می‌ماند.

## معنای نتایج و رسیدگی به خطا

- `started`: شروع؛ وجود شروع بدون پایان پس از crash نتیجه مالی را مشخص نمی‌کند.
- `succeeded`: نتیجه موفق همان عمل؛ HTTP200 یا شارژ کیف پول، پرداخت قطعی سفارش نیست.
- `rejected`: رد معتبر مانند داده نامعتبر، نبود مجوز، تغییر شرایط یا کسری موجودی؛ خطای فنی ناشناخته نیست.
- `failed`: شکست قطعی آن عمل؛ `unknown`/`pending` نتیجه نامشخص/در انتظار است. برای سرویس بیرونی timeout را پرداخت ناموفق قطعی تفسیر نکنید.
- `replayed`: پاسخ درخواست تکراری؛ اثر تجاری و رفتار موفق جدید تولید نمی‌شود.

در افت صف/خطای دیسک، خرید به‌خاطر telemetry متوقف نمی‌شود؛ فضای دیسک، وجود پوشه، دسترسی حساب سرویس و اعداد تنظیمات را بررسی کنید. مقصدی که از ابتدا باز نشده پس از اصلاح تنظیم/مجوز نیازمند restart است. مقصد باز که موقتاً خطای نوشتن دارد در تلاش‌های بعدی دوباره می‌نویسد؛ رویداد ازدست‌رفته backfill خودکار ندارد. `Flush` تخلیه صف است، نه تضمین ثبت در دیسک خراب؛ آمار خطا را نیز ببینید. shutdown معمول صف را تخلیه می‌کند، ولی kill ناگهانی چنین تضمینی ندارد.

حسابرسی الزامی همراه تغییر اصلی در تراکنش دیتابیس است؛ شکست commit موفقیت یا رخداد قطعی نمی‌سازد. فایل لاگ جای ledger یا منبع وضعیت سفارش نیست. برای بررسی تراکنش مالی، وضعیت سفارش/کیف پول و audit دیتابیس مرجع‌اند؛ با تکرار دستی درخواست مالی صرفاً از روی لاگ، وضعیت نامشخص را حل نکنید.

## حدود رفتار مشتری و حریم

رویدادهای view/search درخواست موفق سرورند، نه تضمین مشاهده انسانی یکتا. cart-add تغییر commit‌شده است؛ merge دوباره افزودن شمرده نمی‌شود. quote شروع خرید است؛ placed ثبت سفارش است و paid تنها transition قطعی خرید. paid با شناسه خرید dedupe می‌شود و شارژ/اظهار واریز به‌تنهایی paid نیست.

مهمان فقط با alias سبد موجود شناخته می‌شود؛ برای ثبت بازدید، سبد یا cookie ردیابی تازه ساخته نمی‌شود. بدون سبد یا ورود، شمارش بی‌هویت است؛ اتصال کامل کاربر بین دستگاه‌ها/cohort و ردیاب بیرونی نداریم. نمودار شمار رخدادهاست و ترتیب/نرخ تبدیل یک گروه ثابت را ادعا نمی‌کند. دستگاه فقط desktop/mobile/tablet/unknown است. متن جست‌وجو، UA/IP خام، شماره همراه، نشانی/مختصات، OTP، credential و بدنه request/response ذخیره نمی‌شوند؛ پاکسازی قبل از همه sinkها و در خواندن/export نیز اعمال می‌شود.

## شواهد و بازآزمایی

تست‌ها از fixture و schema موقت PostgreSQL، Redis آزمون و فایل موقت استفاده می‌کنند؛ هیچ پیامک یا پرداخت واقعی لازم نیست. آزمون دیسک خراب با مسیر نامعتبر شبیه‌سازی می‌شود و دیسک کاربر پر نمی‌شود.

```powershell
go -C apps/api test ./...
go -C apps/api vet ./...
npm.cmd --prefix apps/backoffice-web run lint
npm.cmd --prefix apps/backoffice-web run build
```

برای فعال‌شدن تست‌های یکپارچه، `MARKETPLACE_TEST_POSTGRES_URL` باید به دیتابیس آزمون و `MARKETPLACE_TEST_REDIS_URL` به Redis اختصاصی آزمون اشاره کنند؛ از اتصال production استفاده نکنید. `go test -race ./...` در CI لینوکس اجرا می‌شود؛ اجرای race روی Windows این دستگاه به CGO نیاز دارد. [گزارش اجرا](execution.md) تست واقعاً اجراشده را از سناریوهای BDD مستند/اجرانشده جدا می‌کند.
