# CV-LCH-03 — PDP مستقل و انتخاب تنوع/فروشنده؛ بک‌آفیس و سایت

Issue: [#29](https://github.com/MohamadParsa/marketplace/issues/29) · والد: [#11](https://github.com/MohamadParsa/marketplace/issues/11)

## هدف بیزینسی و ترتیب

صفحه مستقل و قابل اشتراک محصول از داده همان پنل ساخته شود و انتخاب مشتری دقیقاً به Variant/Offer قابل خرید برسد.

ترتیب تأییدشده مالک: 3 از۴. وابستگی تحویل: CV-LCH-02؛ آماده‌سازی کارهای مستقل مراحل بعد می‌تواند موازی باشد، ولی پذیرش به همین ترتیب است. مالک/موعد انتساب نشده و تاریخ تحویل فرض نشده است.

## بک‌آفیس

1. فرم محتوای محصول طبق #25: نام فارسی/انگلیسی، متن کوتاه/کامل، مزایا/معایب، published، دسته/برند، دو toggle مستقل نظر/Q&A، ابعاد/وزن، تصاویر، سه متا و noindex/nofollow.
2. اکشن سریع تنوع، قیمت و موجودی و فرم جزئیات موجود #6 حفظ؛ محتوای مشترک از عرضه فروشنده جدا بماند. تصاویر اصلی/گالری/تنوع و ترتیبشان قابل مدیریت باشند.
3. پیاده‌سازی فیلدهای محتوا در همین تسک، ACهای متناظر #25 را هم شاهد بدهد؛ #25 فقط وقتی تمام معیارهای خودش گذشت بسته شود.

## API و داده

1. API عمومی محصول با URL پایدار، محتوای منتشرشده، گالری، محورهای صریح و گزینه‌ها، عرضه‌های قابل نمایش و داده قیمت/ارسال معتبر؛ endpoint خصوصی workspace به مشتری داده نشود.
2. resolver ترکیب و فروشنده server-authoritative؛ عرضه متعلق به همان محصول/تنوع باشد. وزن حمل از وزن طلا جدا، موجودی از انتشار مستقل و متای robots از حریم خصوصی جدا باشد.
3. پردازش متن کامل امن، رسانه معتبر و متادیتای HTML اولیه با روش انتخاب‌شده در قرارداد؛ چهار ترکیب noindex/nofollow مستقل.

## فرانت سایت

1. breadcrumb، گالری، نام، چیپ محورهای تنوع، فروشنده/قیمت بای‌باکس و فهرست سایر فروشنده‌ها با زمان ارسال؛ خصوصیات مهم، متن‌ها و مشخصات طبق A.
2. PDP صفحه مستقل است و reload/deep-link معتبر دارد. دکمه افزودن به سبد و کنترل تعداد مورب مطابق طرح منتخب، فقط برای انتخاب قابل خرید؛ اتصال نهایی سبد در مرحله۴.
3. بخش نظر و پرسش فقط اگر قابلیت و toggle مجاز آماده است فعال باشد؛ ثبت نمایشی یا دکمه بی‌عمل تحویل نشود. خبرم‌کن #17 تا آماده‌شدن فعال نشود؛ ناموجودی با پیام روشن و بدون خرید نمایش داده شود.

## خردکردن کار برای اجرا

قرارداد/مدل و migration → mutation و فرم بک‌آفیس → API عمومی/مشتری → صفحه سایت → بررسی مجوز/خطا/هم‌زمانی مرتبط → شواهد پذیرش. هر زیربخش در همین Issue checklist دارد؛ مرز تحویل، قابلیت متصل است. تغییرات مشترک به Issue اصلی ارجاع داده شوند و دوباره اجرا نشوند.

## معیار پذیرش

- CV-LCH-03-AC01: مدیر محتوای محصول/تصویر/تنوع/عرضه را ویرایش کند و PDP پس از refresh داده درست همان رکورد را نشان دهد؛ قیمت فروشنده دیگر تغییر نکند.
- CV-LCH-03-AC02: انتخاب هر ترکیب/فروشنده به همان Variant/Offer resolve شود؛ ناموجودی یک ترکیب، ترکیب دیگر را از فروش خارج نکند و درخواست ترکیب نامعتبر رد شود.
- CV-LCH-03-AC03: ورود مستقیم و reload روی URL محصول مستقل، گالری/SEO همان محصول و حالت منتشرنشده مطابق قرارداد بدون نشت draft کار کند.
- CV-LCH-03-AC04: طرح A، لوگوی C، CTA و کنترل تعداد مشابه نمونه در۳۹۰/۱۴۴۰ و قرارداد افزودن همان Offer/Variant بررسی شوند؛ مصرف واقعی سبد در مرحله۴ شاهد مستقل دارد و شرط بستن مرحله۳، تکمیل مرحله۴ نیست.
- CV-LCH-03-AC05: اسکریپت در متن/متادیتا اجرا نشود؛ چهار حالت robots مستقل و مرز دسترسی محتوای مشترک در API بررسی شوند؛ تعامل/خبرم‌کن آماده‌نشده فعال نباشند.

## موانع و مرز شروع

R2-Q07 واحدها/رسانه/اعتبارسنجی، R2-Q08 انتشار/robots و R2-Q09 محتوای تعامل؛ بخش مستقل روشن ادامه یابد. فرمول طلا، عرضه نماینده حل‌نشده و قوانین مالی حدس زده نشوند.

مسیرهای مرتبط موجود: CV-R2-06, CV-R2-17. این‌ها ارجاع قابلیت‌اند؛ بسته‌شدن کامل تمام Issueهای مرجع شرط خودکار این تسک نیست. زیرمجموعه استفاده‌شده باید با شاهد پذیرفته شود.

## قرارداد تحویل مشترک

طرح مرجع **A — متعادل و شیک** و لوگو طبق [راهنمای بصری جاری](../../../experiences/storefront/visual-design.md#initial-launch-brand) است؛ نشان C نقش حرف اول Cherriva را دارد. در قفل نوشتاری ترکیبی، C دوباره در کنار نشان تکرار نشود. مرجع تاریخی بدون ویرایش باقی می‌ماند. صفحه محصول مستقل است و دکمه خرید طبق طرح منتخب، نه مودال محصول یا افزودن از کارت خانه/PLP.

هر تسک شامل بک‌آفیس، API/ذخیره‌سازی و فرانت سایت است. frontend با fixture تنها تحویل محسوب نمی‌شود؛ تغییر مجاز بک‌آفیس باید در سایت دیده شود و داده با restart باقی بماند. مخفی‌کردن منو جای کنترل مجوز در سرور نیست. برای هر AC، آزمون مثبت/منفی متناسب و مرور۳۹۰/۱۴۴۰ ثبت شود؛ وضعیت اسناد in-review و اجرای تسک todo است. اطلاعات خصوصی، رسید، نشانی و کیف پول cache عمومی نشوند.

در قرارداد API قبل از اجرا، DTO، validation، خطای فیلدی، unauthorized/forbidden/not-found، تعارض نسخه، pagination و retry مرتبط مشخص شوند؛ پیشنهاد نام جدول/endpoint مجوز تغییر قوانین نیست. loading، empty، error، عدم مجوز و حفظ draft پس از خطا در فرم دیده شوند. داده آزمون ساختگی و با داده عمومی واقعی جدا باشد. بستن کار فقط با شواهد اتصال انتهابه‌انتها، گزارش limitation و تطبیق طراحی مجاز است.
