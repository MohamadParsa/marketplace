# برنامه انتشار اولیه چریوا

هدف تأییدشده مالک: خروجی واقعیِ خانه، PLP، PDP و خرید برای انتشار اولیه و شروع فرایند مجوز. **این برنامه تأیید کافی‌بودن سایت برای مجوز یا زمان صدور آن نیست.** هر خروجی از پنل تا API و سایت متصل است؛ fixture مرورگر یا حافظه resetشونده تحویل عمومی نیست.

هر تسک در همان Issue زیرکارهای قرارداد/داده، بک‌آفیس، API، فرانت و شاهد پذیرش دارد. آماده‌سازی مستقل backend مراحل بعد می‌تواند موازی باشد؛ ترتیب نمایش و پذیرش خروجی خانه → PLP → PDP → خرید است. اتصال لینک به صفحه‌ای که مرحله بعد ساخته می‌شود در گیت نهایی دوباره بررسی می‌شود و dependency دوری نمی‌سازد. مسئول/موعد هنوز تخصیص نیافته؛ تخمین قبلی تعهد تاریخ نیست.

## مرز قطعی انتشار و طراحی

- فقط cherriva.ir؛ طرح **A — متعادل و شیک** برای همه صفحات و فرم‌های این مسیر. [لوگو و رنگ](../../experiences/storefront/visual-design.md#initial-launch-brand): نشان C مطابق طرح قبلی همان حرف اول Cherriva است؛ قفل ترکیبی نباید دو C نشان دهد.
- خانه چهار ریل ثابت دسته‌محور به ترتیب موبایل، هندزفری، پاوربانک و ساعت هوشمند دارد؛ ادمین داده و نگاشت دسته را مدیریت می‌کند، نه صفحه‌ساز. محصولات خانه منتشرشده و دارای عرضه قابل خریدند؛ کمبود با کالای تکراری پر نمی‌شود.
- کارت خانه/PLP فقط به PDP مستقل می‌رود؛ CTA و کنترل خرید مورب مطابق طرح در PDP/سبد است.
- مدل Product/Variant/Offer و حریم فروشگاه حفظ می‌شود؛ این برنامه تعداد فروشنده را به یک محدود نمی‌کند. ارسال ساده بدون اسلات ظرفیت‌دار، هزینه و زمان هر گروه فروشگاهی و یک مقصد مشترک کافی است؛ جزئیات پوشش از داده واقعی پنل می‌آید.
- هر ورودی وجه ابتدا credit کیف پول است؛ مصرف سفارش/عملیات دیگر جداست. در انتشار اول فقط کارت‌به‌کارت با تأیید دستی/بصری واریز در بک‌آفیس فعال است؛ سپس تیم سفارش را تأیید می‌کند. رسید مشتری به‌تنهایی نه شارژ قطعی است و نه پرداخت سفارش.
- موجودی و گردش، شارژ مستقل/رفع کسری و پرداخت سفارش از کیف پول در مرحله۴ هستند. BNPL/درگاه آنلاین، برداشت و refund خودکار، تسویه خودکار، زیرسایت، CMS دستی/استیکی، ظرفیت اسلات و خبرم‌کن شرط این انتشار نیستند؛ نیازمندی‌شان حذف یا done نشده است. تکلیف رسیدگی دستی وجوه/بازپرداخت پیش از استفاده واقعی طبق LCH-Q03 تعیین شود.

## مرز تأیید و پول

اعلام واریز → انتظار بررسی → تأیید دستی/بصری تیم → یک شارژ کیف پول. این عملیات خرید را paid نمی‌کند. اقدام نهایی تأیید سفارش در بک‌آفیس باید اعتبار quote/رزرو/مبلغ مورد قبول مشتری و موجودی قابل مصرف را بسنجد؛ فقط یک برداشت از کیف پول و یک ثبت پرداخت/تأیید سفارش به‌صورت اتمیک انجام شود. اگر وجه پس از انقضا برسد، موجودی کیف پول باقی می‌ماند؛ قیمت جدید یا سبد اصلاح‌شده تأیید مجدد مشتری می‌خواهد. پنل نباید به‌اجبار سفارش با مبلغ متفاوت را نهایی کند.

LCH-Q01 با پاسخ مستقیم مالک حل شده است. LCH-Q02 (مدرک/مبلغ/مرجع)، LCH-Q03 (وجوه/استرداد) و LCH-Q04 (رزرو در انتظار بررسی) فقط بخش مالی وابسته را متوقف می‌کنند؛ کار مستقل خانه/کاتالوگ/نشانی ادامه یابد. [دفتر پرسش‌ها](../../product/open-questions.md#initial-launch-questions)

چهار Issue جدید **برش اجرایی کارهای مادر** هستند؛ به۱۷ شرح اصلاحات، چهار نیازمندی موازی تکراری اضافه نشده است. فهرست۱۷تایی سابقه کارهای مادر و این فهرست صف عملی اجرای انتشار است. هیچ کار مادر صرفاً به‌خاطر بسته‌شدن برش ناقص، انجام‌شده اعلام نمی‌شود.

## گیت انتشار عمومی

1. خروجی واقعی چهار تسک و شاهد هر AC؛ لینک خانه/PLP/PDP و سبد انتهابه‌انتها بدون کنترل جعلی.
2. ذخیره پایدار، migration و backup/restore، تنظیم production و جدایی داده fixture؛ API مشتری از gate local/test خارج و با مجوز صحیح پذیرفته شده باشد.
3. خطاهای قیمت/موجودی، انقضا، دو درخواست هم‌زمان، اعلام واریز، رد/تأیید، retry و دفتر گردش مالی بررسی شوند.
4. مقصد کارت و متن معرفی/تماس/رویه خرید/ارسال/مرجوعی/حریم خصوصی واقعی، رسانه معتبر، DNS/HTTPS و رابط موبایل/دسکتاپ مطابق A.
5. اطلاعات خصوصی/رسید و OTP آزمون عمومی نشوند؛ برداشت واقعی و ثبت مالی از fixture/موفقیت ساختگی ساخته نشوند.
6. مرجع مجوز، نوع فعالیت و دامنه فروش عمومی قبل از انتشار بررسی شوند؛ این چک‌لیست فنی جای تأیید مرجع صدور نیست.
