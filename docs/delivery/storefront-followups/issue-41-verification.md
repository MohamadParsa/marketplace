# تحویل #41 و اصلاحات همراه

مسیر سورس و اجرای محلی `D:\Cherriva` است. [Issue #41](https://github.com/MohamadParsa/marketplace/issues/41) کش عمومی را پوشش می‌دهد؛ اصلاح جدول‌ها/درخت و پاک‌سازی کاتالوگ با پیام‌های تکمیلی مالک به همین تحویل افزوده شدند. [#42](https://github.com/MohamadParsa/marketplace/issues/42) برای chr/slug همچنان مستقل و انجام‌نشده است. طرح **A — متعادل و شیک** و نشان C حفظ شدند. انتشار Liara در این تحویل انجام نشده است.

## نتیجه اجرایی

- زیر بنر فقط ریشه‌های دارای کالای منتشر/قابل خرید در خود یا زیرشاخه می‌آیند. ریشهٔ بی‌فرزند مانند موبایل حذف نمی‌شود. والد ریل‌های منتخب اولویت دارند، سپس تعداد کالا و نام/شناسه ترتیب پایدار می‌دهد. تعداد میان‌بر ابتدا از۱۴۶ به۳۷ و پس از حذف داده نمونه به **۲۸ ریشه واقعی** رسید. نمای اولیه هشت مورد در یک ردیف قابل پیمایش است؛ بقیه با «مشاهده همه دسته‌ها» در دسترس‌اند. درخت واقعی داده جابه‌جا نشده و PLP مادر همچنان فقط محصولات مستقیم خودش را نشان می‌دهد.
- Redis اختیاری، مشترک بین سایت/بک‌آفیس و فقط برای DTO عمومی است. کلید محصول شامل نسخه محصول/وابستگی است؛ خانه/لیست generation مشترک دارند. نسخه با query کوچک از PostgreSQL خوانده می‌شود. rollback یا قطع Redis پس از commit، نسخه معتبر را گم نمی‌کند؛ old fill نسخه تازه را آلوده نمی‌کند.
- محصول با انتخاب variant/offer معتبر کش می‌شود. کارت‌ها در پاسخ کوچک خانه/PLP کش می‌شوند؛ کلید جداگانه برای تک‌تک کارت‌ها اضافه نشده تا درخواست‌های N+1 ایجاد نشود. قیمت، موجودی، انتشار، فروشنده، رسانه، دسته و وابستگی‌های مشترک تمام نماهای متأثر را باطل می‌کنند. مالی/سبد/انتخاب خرید/نشست/OTP/مجوز وارد Redis نمی‌شوند.
- migrationهای افزایشی `000005` و `000006`، نمای کاتالوگ پاک از هویت/مالی، نسخه‌های پایدار، اجازه رسانه و snapshot عمومی آماده را می‌سازند؛ workspace اصلی، هویت و دفتر مالی جایگزین نمی‌شوند. مسیر واردات فایل هم همان نسخه‌گذاری را اجرا می‌کند. تغییر یک محصول، نسخه مستقل محصول بی‌ارتباط را عوض نمی‌کند؛ بعضی وابستگی‌های مشترک عمداً همه PDPها را باطل می‌کنند.
- بررسی مجوز تصویر عمومی از index پایدار و blob جدا انجام می‌شود؛ ETag فقط بعد از کنترل visibility بررسی می‌شود. preview خصوصی نیز با مجوز جاری و خواندن سبک هویت انجام می‌شود؛ cache عمومی ندارد. باینری در Redis کپی نشده است. خواندن هویت هم به بارگذاری کل کاتالوگ وابسته نیست.
- بررسی انقضای خرید از query کوچک سررسید استفاده می‌کند؛ انقضای واقعی و آزادکردن موجودی با همان تراکنش حوزه انجام می‌شود. اعلان expire در Redis مرجع رزرو نیست.
- گریدهای پنل و لیست کاتالوگ صفحه‌بندی۲۰/۵۰/۱۰۰، جست‌وجو و ویرایش واضح دارند؛ اکشن‌ها با ستون ثابت و قابل wrapping دیده می‌شوند. فرم دسته و انتخاب دسته محصول، درخت/مسیر و جست‌وجو دارند. والد در ویرایش فعلی فقط نمایش داده می‌شود؛ backend قبلی جابه‌جایی والد را اجازه نمی‌داد و این تحویل آن قاعده را عوض نکرده است. صفحه‌بندی فعلی **کلاینتی** است؛ حذف رندر هم‌زمان هزاران ردیف و تصویر انجام شد، اما پاسخ workspace پنل هنوز بزرگ است.

## سیاست و راه‌اندازی

TTLهای پیش‌فرض: خانه/بنر۳۰۰ثانیه، محصول۶۰۰، PLP/search۶۰، پیشنهاد۳۰. تنظیم محیطی فقط اجازه کوتاه‌کردن تا سقف مصوب می‌دهد. cache miss، مقدار خراب یا قطع Redis از مرجع پاسخ می‌گیرد؛ circuit breaker پنج‌ثانیه‌ای، تلاش شبکه محدود۱۰۰ms، singleflight و حداکثر۴ ساخت هم‌زمان در هر پردازه وجود دارد. قفل توزیع‌شده و cache داده خصوصی اضافه نشده‌اند.

**هر startup سایت** warmup غیرمسدودکننده اجرا می‌کند: خانه و بنر، چهار PLP، سپس حداکثر۱۰۰ محصول اولویت‌دار با۲worker و بودجه۴۵ثانیه. همه محصولات دیگر هنگام اولین درخواست کش می‌شوند؛ warmup شامل پیش‌بارگذاری تمام۳۵۳۴PDP یا باینری تصاویر نیست. قطع Redis warmup را skip می‌کند و listener سایت بالا می‌آید. shutdown کارهای warmer را لغو می‌کند. شمارنده hit/miss/build/error/retry و خواندن/زمان SQL/decode هر دقیقه در لاگ سرور ثبت می‌شوند؛ داده حساس چاپ نمی‌شود.

روی سیستم فعلی، راه‌انداز Redis۷ موجود در WSL را فقط روی loopback و پورت اختصاصی بررسی بالا می‌آورد؛ maxmemory=۱۲۸MiB و allkeys-lru، بدون ذخیره دیسکیِ کش. سرویس ناشناس روی همان پورت متوقف یا flush نمی‌شود. `REDIS_URL` خصوصی موجود در محیط بر راه‌اندازی خودکار مقدم است. نبود Redis/WSL مانع اجرای PostgreSQL نیست. [راهنمای اجرای کامل](../../local-development.md).

```powershell
Set-Location D:\Cherriva
.\Start-Cherriva.ps1
# اگر frontend فعلی از قبل build شده:
.\Start-Cherriva.ps1 -NoBuild
# اجرای بدون Redis:
.\Start-Cherriva.ps1 -NoBuild -NoCache
```

## اندازه‌گیری محلی؛ پیش از پاک‌سازی جداگانه داده نمونه

همه مقایسه‌های این جدول روی **همان۳۵۸۰محصول**، همان endpoint/بدنه و دستگاه،۳۰نمونه در هر حالت و هم‌زمانی۱ انجام شدند؛ بعداً۴۶نمونه قدیمی پاک شد. زمان‌های cold شامل miss واقعی با حذف فقط کلیدهای عمومیِ Redis محلی پیش از هر نمونه است؛ هزینه فرمان حذف خارج از زمان HTTP است. هیچ `FLUSHALL` اجرا نشده است. [اسکریپت قابل بازتولید](../../../tests/performance/public-catalog-cache.cjs) و [نتیجه ماشین‌خوان](issue-41-checks.json).

| API / p95، میلی‌ثانیه | قبل | پس از تغییر، cold | پس از تغییر، warm |
| --- | ---: | ---: | ---: |
| خانه | ۱۹۳۵٫۸ | ۴۹۱٫۶ | ۳٫۵ |
| PLP موبایل | ۱۰۱۳٫۳ | ۳۸۷٫۵ | ۲٫۵ |

هیچ نمونه HTTP این اندازه‌گیری خطا نداشت. p95 workspace خصوصی بک‌آفیس از۶۶۷٫۳ به۴۴۷٫۹ms رسید؛ اندازه پاسخ حدود۱۳MB باقی ماند. این عدد API است، نه کل زمان لود صفحه یا SLA سرور. RSS جاری پس از مرور، حدود۳۱MiB سایت و۲۵MiB پنل بود؛ peak محلی سایت حدود۳۲۷MiB ثبت شد. baseline RSS پیش از تغییر ثبت نشده و مقایسه حافظه یا ظرفیت production ادعا نمی‌شود.

## پاک‌سازی و نام‌های فروشگاه

فقط allowlist دقیقِ snapshot خصوصی **پیش از ورود کاتالوگ** استفاده شد؛ «هر شناسه‌ای که gsp نیست» معیار حذف نبود. دسته‌ها/محصولات تازه یا ناشناس بیرون این فهرست هدف قرار نگرفتند. SHA فایل اصلی با manifest برابر ماند. ابتدا dry-run، بررسی وابستگی و سپس تغییر با `Repository.Update` در تراکنش انجام شد؛ SQL مستقیم برای حذف/جایگزینی داده کسب‌وکار یا اتصال مجدد به SQL Server مبدأ استفاده نشد. پشتیبان خصوصی baseline پیش از ورود و۴۲رسانه قدیمی در runtime محفوظ است؛ در Git قرار نگرفته است.

| حذف‌شده | تعداد |
| --- | ---: |
| محصول / دسته / برند | ۴۶ / ۲۰ / ۳ |
| خصوصیت / تنوع / عرضه | ۱۱ / ۵۹ / ۷۶ |
| رسانه بدون مرجع باقی‌مانده | ۳۶ |

نتیجه:۳۵۳۴محصول،۲۴۸دسته،۱۲۷۷برند،۲۴۲ویژگی،۵۰۲۹تنوع و۵۹۹۲عرضه واردشده باقی‌اند.۴فروشگاه عملیاتی وابسته به حساب‌ها/سوابق و۶رسانه مورد استفاده تاریخچه حفظ شدند. کاربران و رمزها، نقش‌ها/عضویت، سفارش‌ها، quote، کیف پول/دفتر مالی، واریز/رسید/بازپرداخت، آدرس و بانک/ارسال پاک نشدند. بازدید آزمون مرورگر سبد مهمان می‌سازد و خط سبد را اضافه/کم/پاک می‌کند؛ پس برابری hash کل workspace انتظار درستی نیست. هیچ سفارش یا پرداخت واقعی برای این آزمون ثبت نشده است.

نام هر۴۴فروشگاه واردشده با [نگاشت غیرواقعی](../catalog-seed/store-aliases.json) جایگزین شد؛ شناسه، مدل، وقفه، مالکیت و عرضه تغییر نکرد. نام‌ها مانند «فروشگاه چریوا ۱۷۲» از شناسه پایدار مشتق می‌شوند. CLI واردات از این پس به‌طور پیش‌فرض `-anonymous-stores=true` دارد؛ fingerprint و فایل منبع اصلی تغییر نمی‌کند، retry همان snapshot همچنان already_applied است و نام واقعی برنمی‌گردد. نگاشت ذخیره‌شده اصلی، داده استخراج تاریخی است؛ نام نمایشی مقصد با سیاست جدید اعمال می‌شود.

تنها یک ارجاع به دستهٔ نمونهٔ حذف‌شده از تنظیمات فعلی روش محلی پاک شد؛ سه شاخه `gsp-cat-828/831/878` و زیرشاخه‌هایشان همچنان ممنوع‌اند. سقف محلی۳۰میلیون و کارت‌به‌کارت۱۵میلیون تومان و تمام اطلاعات بانکی/مالی حفظ شدند؛ snapshot روش پرداخت در سوابق قدیمی بازنویسی نشد.

بررسی نهایی تمام فیلدهای کاتالوگ واردشده را با همان decode/validation واردات، و فروشگاه‌ها را با استثنای نام‌های نمونه، تطبیق داد.۱۰٬۰۵۸تصویر واردشده با۳٬۳۴۹٬۳۸۷٬۲۸۹بایت باقی‌اند. تکرار پاک‌سازی بدون حذف دوباره، already_applied=true و تغییر نام صفر داد. [جزئیات۲۱کنترل حفاظت/تطبیق](issue-41-checks.json).

## آزمون و شواهد

- Go:۲۰۳تست/زیرتست موفق، صفر fail؛ تست‌های PostgreSQL و Redis واقعی اجرا شدند. تنها تست اختیاری `TestCatalogSnapshotPostgresRoundTrip` که به cache خصوصی حجیم وابسته است skip شد؛ این تحویل آن roundtrip چندگیگابایتی را دوباره اجرا نکرد. `go vet ./...` موفق. race محلی Windows اجرا نشده؛ نتیجه CI جدا ثبت می‌شود.
- lint/typecheck و build هر دو frontend موفق؛ هشدار پیشین chunk بزرگ بک‌آفیس غیرمسدودکننده است.
- [۳۳کنترل رابط جدید](../../../tests/e2e/public-cache-review.cjs) و [۷۶کنترل کاتالوگ/تنوع/سبد](../../../tests/e2e/catalog-seed-review.cjs): **۱۰۹از۱۰۹**، بدون runtime pageerror. هر دو روی داده پاک‌شده اجرا شدند. آزمون ایجاد/ویرایش فرم، cancel شد و کالای تازه نساخت؛ سبد آزمون در پایان خالی شد.
- راه‌اندازی با Redis غیرقابل اتصال هم خانه/PLP/PDP/تصویر۲۰۰ برگرداند و warmer skip شد؛ سپس راه‌اندازی عادی تکرار و warmup۱۰۰محصول/۴PLP با صفر خطا مشاهده شد. داده پس از restart باقی ماند.
- رقابت fill/write، idempotency/rollback، نسخه دو پردازه، تغییر قیمت/موجودی، import، انقضا، visibility با ETag قدیمی، خرابی مقدار کش، قطعی و سقف TTL با ساعت کنترل‌شده، مجوز فعلی preview و عدم بازنویسی کسب‌وکار هنگام backfill، تست مستقل دارند.

## محدودیت و بازگشت

صفحه‌بندی پنل در این نسخه از state فعلی است؛ endpoint صفحه‌ای و حذف payload بزرگ پنل هنوز انجام نشده است. باینری‌ها همان تصاویر مقصد هستند و thumbnail/CDN جدید اضافه نشده؛ زمان/حجم انتقال تصویر روی اینترنت با Redis حل کامل نمی‌شود. Redis فقط JSON عمومی دارد. ذخیره نمای عمومی هزینه نوشتن/فضای اضافه دارد؛ در بار واقعی بعدی، write amplification و حافظه دوباره اندازه‌گیری شوند.

برای خاموش‌کردن کش، `PUBLIC_CACHE_ENABLED=false`؛ برای فقط خاموش‌کردن warmup، `CACHE_WARMUP_ENABLED=false`. در همان PowerShell، `-NoCache` مقدار env را false می‌کند؛ برای فعال‌سازی دوباره آن را true/پاک و راه‌انداز را اجرا کنید. migrationها حتی در حالت بدون Redis لازم‌اند. rollback کش به معنی حذف داده/جدول مالی یا بازگرداندن workspace قدیمی نیست؛ خروجی‌های public قابل بازسازی‌اند. استقرار عمومی، پذیرش #12 و تغییر URL #42 مستقل‌اند.

## اصلاح بنرهای ساعت و پاوربانک؛ درخواست تکمیلی مالک

دو بنر مکمل قبلی به دسته‌های نمونهٔ پاک‌شده اشاره می‌کردند. هر دو به حالت `catalog_category_id` متصل شدند: ساعت `gsp-cat-755` و پاوربانک `gsp-cat-163`. عکس از اولین محصول واقعاً موجود همان ریل، و لینک از URL همان ریل می‌آید؛ عکس یا مقصد نمونهٔ قدیمی استفاده نمی‌شود. چیدمان HTML/CSS پاسخ‌گو و طرح A است؛ فایل تصویری مصنوعی تازه ساخته نشده است. در نبود کالای موجود، بنر پنهان می‌شود.۴asset بدون مرجع بنر مکمل حذف شد؛ بنر اصلی فعال و اطلاعات مالی تغییر نکردند.

در پنل بنر، منبع تصویر با دکمه‌های چهار دستهٔ ریل یا «تصویر ثابت» انتخاب می‌شود. برای حالت کاتالوگ، دو فایل جدا لازم نیست؛ برای تصویر ثابت، همان کنترل‌های قبلی دسکتاپ/موبایل و انتشار مستقل باقی‌اند. backend دسته منتشر و جزو۴ریل بودن را enforce می‌کند؛ preview عمومی هم از همان عکس و مقصد موجود استفاده می‌کند. با تغییر schema پاسخ، کلیدهای کش به `public:v2` تغییر کردند تا پاسخ نمونه قدیمی مجدداً مصرف نشود.
