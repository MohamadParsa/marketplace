# آدرس عمومی کاتالوگ — CV-CAT-PUBLIC-URL-01

Issue: [#42](https://github.com/MohamadParsa/marketplace/issues/42) · مسئول: `eliassarband` · وضعیت اجرا: **todo**

## نتیجه و خواسته قطعی مالک

پیشوند `gsp` از کد و URL عمومی محصولات چریوا حذف شود و آدرس دسته با نام انگلیسی و dash خوانا شود. این سند و Issue مربوط فقط **برنامه اجرا** هستند؛ هیچ شناسه، URL یا دیتایی در این تحویل عوض نشده است.

| موجود | مقصد درخواست‌شده / نمونه |
| --- | --- |
| `/product/gsp-product-18189` | **`/product/chr-18189`**؛ نمونه صریح مالک، با حفظ شماره محصول واردشده |
| `/product/gsp-product-37354` | `/product/chr-37354` با همان قاعده؛ نه نگاشت حدسی به chr-2222 |
| `/category/gsp-cat-1`، گوشی موبایل | `/category/mobile` |
| `/category/gsp-cat-755`، ساعت هوشمند | پیشنهاد slug: `/category/smart-watch`؛ این دسته نباید به mobile نگاشت شود. |

`chr-2222` مثال قالب اولیه بود؛ نمونه بعدی مالک حفظ suffix عددی `18189` را روشن کرد. `smart-watch` و slug سایر دسته‌ها پیشنهاد فنی/محتوایی‌اند و نیاز به فهرست قابل بازبینی دارند؛ نام فارسی/انگلیسی محصول و دسته حذف نمی‌شود.

## مدل و مرز فنی پیشنهادی

- `Product.ID` شناسه داخلی پایدار بماند؛ فیلد/نگاشت عمومی یکتای `public_code` مانند `chr-18189` اضافه شود. جایگزینی متن سراسری `gsp` و تغییر کلیدهای موجود مجاز نیست. Variant، Offer، media، membership، cart، quote، سفارش و سابقه مالی روابط فعلی را نگه دارند.
- برای محصولات واردشده، public code از suffix عددی معتبر `gsp-product-{n}` ساخته و یکتایی بررسی شود. این قاعده برای product است؛ SKU فروشنده، variant و شناسه تصویر خودکار تبدیل نشوند. تعارض با کد موجود، migration را متوقف و conflict report بدهد؛ کد دیگری بی‌صدا انتخاب نشود.
- محصول بومی/غیرعددی موجود و محصول جدید با sequence پایدار PostgreSQL کد بگیرد؛ **پیشنهاد شروع: بزرگ‌تر از بزرگ‌ترین شماره عمومی رزروشده در backfill**. شماره‌ها حداقل چهاررقمی، بدون محدودیت چهاررقمی، بدون صفر پیشرو، فقط ASCII و افزایشی باشند؛ gap مجاز و کد حذف‌شده دوباره استفاده نشود. این جزئیات sequence پیشنهادند؛ نمونه قالب، سقف عدد یا مجوز تولید کد تصادفی نیست.
- نگاشت محصول↔شماره در مخزن پایدار با unique constraint برای هر دو سمت و تخصیص اتمیک ثبت شود؛ در ساختار aggregate فعلی، جدول projection مستقل گزینه ساده‌ای است. شمارنده از `len(products)+1`، timestamp یا Redis ساخته نشود. cache miss و restart کد تازه تولید نکنند.
- `Category.Slug` فیلد مستقل باشد؛ مقدار پیش‌فرض از نام انگلیسی نرمال‌شده: lowercase، تبدیل فاصله/underscore به dash، ادغام dashهای پشت‌سرهم و حذف dash ابتدا/انتها. قرارداد پیشنهادی `[a-z0-9]+(?:-[a-z0-9]+)*` تا۱۰۰نویسه؛ تغییر نام انگلیسی بعداً slug را خودکار عوض نکند.
- چون مسیر flat است، slug در تمام دسته‌ها یکتا باشد، نه فقط بین خواهر/برادر. مقدار خالی، تکراری، فقط dash، نویسه نامعتبر و collision با alias قبلی در سرور رد شوند؛ فرم نیز پیام روشن داشته باشد. نام انگلیسی غایب یا دو نام یکسان، فهرست تصمیم محتوایی می‌خواهند؛ حدس ترجمه یا slug موقت عمومی بی‌اجازه ساخته نشود.
- کاربر URL با slug می‌بیند؛ سرویس آن را به ID داخلی resolve می‌کند. فیلترها، درخت و payment-category restrictions همچنان ID داخلی دارند؛ قاعده «فقط محصولات منتسب به خود دسته» PLP تغییر نکند. parent/child در breadcrumb حفظ شود.

## مهاجرت، لینک قبلی و SEO

1. پیش از apply گزارش dry-run نگاشت تمام محصولات/دسته‌های موجود، کدهای غیرعددی، نام انگلیسی خالی و collisionها تولید شود؛ صورت‌جلسه اصلاح موارد باز و backup در محیط هدف داشته باشد.
2. migration افزایشی و transaction-safe؛ backfill تکرارشونده کدها را دوباره تخصیص ندهد. شماره source و ID داخلی برای importer/idempotency حفظ شوند. فایل JSON، manifest/SHA و snapshot تاریخی بازنویسی نشوند. همه کاربران، عرضه/موجودی، سفارش‌ها، wallet و bank حفظ شوند.
3. `/product/{public_code}` و `/category/{slug}` مسیر canonical شوند. URL قدیمی با **redirect دائمی سروری 301** مستقیم به مسیر جدید همان موجودیت برود، بدون زنجیره و بدون open redirect. پارامتر مجاز variant/offer و query فیلتر/مرتب‌سازی حفظ/validate شود؛ مقصد از نگاشت معتبر سرور ساخته شود.
4. draft، شاخه پنهان و رکورد حذف‌شده از راه resolve قدیمی هم عمومی نشوند؛ همان 404/قواعد عدم‌انتشار فعلی. برای mutation/POST، redirect301 مرورگری استفاده نشود؛ مرز API شناسه داخلی را حفظ کند یا resolver سازگار و صریح بدهد. فقط لینک عمومی جدید منتشر شود، نه ID داخلی.
5. لینک کارت‌های خانه/PLP/جست‌وجو/پیشنهاد، ریل/تخفیف، دسته‌های زیر بنر، breadcrumb، PDP، سبد، لینک سفارش و لینک اشتراک از helper واحد URL استفاده کنند. تمام سطح‌های public DTO شامل URL جدید باشند؛ مجبورکردن frontend به بریدن رشته source ID مجاز نیست.
6. canonical، SEO HTML اولیه و sitemap در صورت وجود، مسیر جدید بدهند؛ sitemap تازه اگر لازم شد در دامنه همین کار مشخص شود. policy noindex محیط بررسی و تنظیم noindex/nofollow محصول حفظ شود.
7. slug توسط ادمین مجاز قابل مشاهده/ویرایش باشد؛ تغییر slug منتشرشده تأیید صریح، version check، audit و alias دائمی آدرس قبل می‌خواهد. public code محصول پس از تخصیص فقط‌خواندنی باشد؛ تغییر معمول محتوا/نام کد را عوض نکند. پیش‌نمایش URL در فرم‌های طرح A اضافه شود؛ بدون dropdown تازه.
8. نسخه DTO/کلیدهای کش عمومی و لینک‌های cacheشده پس از migration تازه شوند؛ cache محصول بر ID داخلی تکیه کند تا تغییر URL هویت cache را دوپاره نکند. با [کش](cache-policy.md) هماهنگ شود؛ اجرای این کار به روشن‌بودن Redis وابسته نیست.

## مجوز، خطا و حالت‌های مرزی

افزودن/ویرایش slug فقط با مجوز کاتالوگ دسته موجود؛ seller با URL جدید حق محتوای مشترک پیدا نمی‌کند. تعارض slug/code با409، قالب نامعتبر400، شناسه ناشناخته/پنهان404 و نسخه قدیمی409 طبق قرارداد endpoint مربوط نگاشت شود. عدم موفقیت، نام/slug/alias پیشین را حفظ کند. رابط حالت ذخیره/خطا و پیش‌نمایش داشته باشد. lookup URL ورودی، SQL parameterized و محدودیت طول داشته باشد؛ عمومی‌بودن کد جای کنترل مالکیت نیست.

برای محصول بومی با ID غیرعددی، تخصیص یک بار در backfill؛ برای دو ساخت هم‌زمان، unique/sequence ضامن یکتایی؛ برای محصول حذف‌شده، کد محفوظ و مقصد عمومی مطابق حذف؛ برای دسته هم‌نام، conflict آشکار و slug انتخابی ادمین؛ برای تغییر دوباره slug، همه aliasهای گذشته به مقصد جاری resolve شوند و حلقه ایجاد نشود. aliasهای قدیمی قابل تصاحب توسط رکورد جدید نباشند.

## زیرتسک‌ها به ترتیب اجرا

- [ ] URL-01: گزارش نگاشت همه داده‌ها و تأیید slugهای غایب/متعارض؛ نام واقعی دسته755 حفظ شود. مشخص‌کردن sequence محصولات بومی و قاعده حداقل۴رقمی پیشنهادی.
- [ ] URL-02: مدل و migration افزایشی نگاشت public code، sequence و unique constraint؛ Category.Slug و alias پایدار؛ dry-run/backfill idempotent.
- [ ] URL-03: resolver و builder مشترک API/HTML، redirectهای سروری و کنترل visibility؛ API mutation و روابط داخلی سازگار بمانند.
- [ ] URL-04: فرم دسته در بک‌آفیس، کد فقط‌خواندنی محصول، پیش‌نمایش/اعتبارسنجی/مجوز/version/audit؛ طراحی A.
- [ ] URL-05: لینک‌های storefront و SEO/اشتراک/سبد/سفارش، breadcrumb و query انتخاب تنوع؛ invalidation لینک‌های کش.
- [ ] URL-06: تست مهاجرت/replay/restart/رقابت/سازگاری و مرور خانه/PLP/PDP/سبد؛ مستندات اجرای local/سرور، کامیت سورس و مدارک و PR؛ انتشار توسط پارسا جداست.

## پذیرش

- AC01: محصول نمونه18189 از `/product/chr-18189` باز شود؛ مسیر قبلی تنها یک301 به همان محصول بدهد. 37354 نیز chr-37354 بگیرد. مدل داده منبع یا order/item IDs بی‌دلیل rename نشوند.
- AC02: دسته موبایل `/category/mobile` و دسته ساعت هوشمند slug تأییدشده خودش را داشته باشد؛ اجداد، فرزندان، فیلتر و breadcrumb به همان دسته فعلی اشاره کنند. دسته غیرفعال از alias قبلی قابل مشاهده نشود.
- AC03: همه محصول‌ها و دسته‌های موجود گزارش نگاشت کامل/تعارض روشن داشته باشند؛ public code و slug یکتا، ثابت در ویرایش/restart/replay و ایمن در تخصیص هم‌زمان باشند. importer همان snapshot را دوباره وارد کند بدون ساخت محصول یا کد مضاعف.
- AC04: لینک‌های داخلی/SEO جدید `gsp-product` و `gsp-cat` را به عنوان URL canonical منتشر نکنند؛ این رشته‌ها در ID داخلی/سابقه واردات مجاز بمانند. variant/offer و فیلتر مجاز پس از redirect حفظ شوند؛ مورد نامعتبر و alias collision آزموده شوند.
- AC05: سبد قبلی، سفارش، رزرو، عرضه/قیمت/موجودی، تصاویر، محدودیت پرداخت محلی طلا و سقف روش‌ها حفظ شوند؛ هیچ سابقه مالی یا حسابی جابه‌جا نشود.
- AC06: دسته‌های بدون نام انگلیسی، slug تکراری و کدهای غیرعددی قدیمی در dry-run و UI پیام روشن داشته باشند؛ شکست migration داده قبلی را دست‌نخورده بگذارد. فروشنده/کاربر غیرمجاز با تغییر URL حق تازه نگیرد.
- AC07: تست redirect HTTP واقعی و HTML canonical با تست مرورگر۳۹۰/۱۴۴۰ و لینک نمونه، راهنمای migration و rollback غیرمخرب، شماره کامیت‌ها و نتیجه CI ثبت شوند؛ ایجاد این سند معادل تکمیل این ACها نیست.

## اولویت و وابستگی

P2 پیشنهادی بعد از رفع مشکل دسته‌های خانه و کارایی؛ داده/مالی و قالب URL دقیق، گیت صحت این کارند. این تکمیل جدید #28/#29 است، نه بازاجرای نیازمندی #24/#25. اولین زیرتسک قبل از apply متوقف می‌شود اگر slug دسته یا conflict حل‌نشده باقی باشد؛ بخش مستقل مدل/گزارش قابل انجام است. تأیید جزئیات فنی و slugها هنوز باز است.
