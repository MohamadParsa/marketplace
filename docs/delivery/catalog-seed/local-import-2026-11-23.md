بسته کامل با دستور صریح مالک در **دیتابیس بررسی محلی چریوا از سورس `D:\Cherriva`** وارد شد. اتصال به SQL Server مبدأ انجام نشد؛ فایل snapshot تغییر نکرد. سرور و Liara تغییری نگرفتند. [شواهد ماشین‌خوان](local-import-2026-11-23.json) · [بسته و دستورها](README.md).

## اجرا و نتیجه

۱. SHA-256 فایل با manifest تطبیق داده شد: `c8154676f86f134c0ba98c7f53a7614e38f0c6cad2828b83e61b82eccdfbee98`، اندازه۵۰٬۵۷۳٬۸۱۴بایت.
۲. dry-run ابزار موجود موفق بود. پیش از migration و ورود، نسخه پشتیبان و digest اطلاعات موجود در مسیر خصوصی runtime ثبت شد؛ این نسخه و اطلاعات اتصال وارد گیت نشده‌اند.
۳. migration000004 با حفظ رجیستری سه migration قبلی اجرا شد. workspace موجود حفظ شد؛ fixture یا حساب تازه جایگزین آن نشد.
۴. فرمان کامل بدون `limit-products` اجرا شد؛ `applied=true`، `mode=review` و `configure_home=true`. تصاویر cache با checksum بررسی، decode و در جدول رسانه مقصد ذخیره شدند.
۵. **همان فرمان** دوباره اجرا شد: `already_applied=true` و `applied=false`؛ ردیف یا audit ورود تکراری ساخته نشد.
۶. PostgreSQL و هر دو سرویس API متوقف و دوباره راه‌اندازی شدند. تطبیق تمام۱۶۳۶۶رکورد کاتالوگ بسته با نگاشت نهایی، بررسی API و حفظ اطلاعات قبلی دوباره موفق بود. هر دو سطح HTTP200 می‌دهند.

## حفظ اطلاعات و استثنای طبیعی انقضا

بلافاصله پس از import و پیش از مرور صفحات، مقایسه دقیق تأیید کرد که کاربران، hash رمزها، نقش‌ها، عضویت‌ها، سفارش‌ها، اطلاعات مالی، تنظیمات و اقلام قبلی کاتالوگ تغییر نکرده‌اند. پس از restart هم ۲۱ کاربر، ۵ نقش، ۵ عضویت، ۹ انتساب نقش، ۱۱ ردیف کیف پول، ۷ اعلام واریز و ۷ رسید با همان محتوای قبلی وجود دارند. اطلاعات بانک، ارسال، جغرافیا، مشخصات کسب‌وکار و بنرهای موجود عیناً حفظ شدند؛ بنر/کمپین گوشی‌شاپ فعال نشد.

یک quote قدیمی از روز قبل هنوز `reserved` بود. هنگام اجرای عادی برنامه، سیاست مصوب۳۰دقیقه آن را `expired` کرد، خرید وابسته را `requires-reconfirmation` کرد و رزرو همان موجودی قدیمی را آزاد کرد. این رفتار **پس از import و توسط روال عادی برنامه** رخ داد؛ سفارش/قلم/وجهی حذف نشد، مبلغ پرداخت و دفتر مالی تغییر نکرد. در مقایسه نهایی فقط همین انتقال وضعیت و event سیستم، به‌علاوه تغییر مجاز نگاشت روش پرداخت و سبد مهمانِ آزمون، به‌صورت مشخص تفکیک شدند. رکوردهای قدیمی سبد دست‌نخورده‌اند؛ سبد مهمان آزمون در پایان خالی شد. سفارش یا شارژ جدید ثبت نشد.

## سه اصلاح لازم برای داده واقعی

- **تومان فایل و ریال داخلی:** ابزار قبلی تبدیل مرزی را نداشت. `DecodeCatalogSeed` اکنون قیمت و قیمت خط‌خورده تومانی را دقیقاً یک بار در۱۰ ضرب می‌کند؛ validation/retry دوباره تبدیل نمی‌کنند. حد مبلغ و overflow کنترل می‌شوند. فایل و SHA اصلی عوض نشدند. تمام۵۹۹۲عرضه مقصد با مقدار صحیح داخلی تطبیق داده شدند؛ قیمت نمایشی هفت PDP هم با تومان فایل برابر بود.
- **checksum migration در Windows/Linux:** migration اول قبلاً با CRLF ثبت شده بود. runner اکنون فقط تفاوت LF/CRLF را می‌پذیرد؛ تغییر SQL، فاصله یا کامنت همچنان رد می‌شود. hash ثبت‌شده قدیمی بازنویسی نشد؛ فایل‌های SQL تاریخی تغییر نکردند. تست اختصاصی PostgreSQL این سازگاری و رد تغییر واقعی را تأیید کرد.
- **گزینه تنوع در PDP:** تعریف مشترک رنگ/گارانتی می‌تواند مقادیر زیادی داشته باشد. پاسخ عمومی PDP اکنون فقط مقادیری را نشان می‌دهد که در تنوع‌های همان محصول تعریف شده‌اند؛ گزینه تعریف‌شده ولی ناموجود حذف نمی‌شود. تعریف مشترک و فرم بک‌آفیس تغییر نمی‌کنند. این اصلاح از نمایش رنگ/گارانتی محصولات دیگر جلوگیری کرد.

## محدودیت روش‌های پرداخت

سقف‌های موجود درست بودند و تغییر نکردند: کارت‌به‌کارت۱۵میلیون و محلی۳۰میلیون تومان، روی **کل سفارش همراه ارسال**. فقط شناسه‌های `gsp-cat-828`، `gsp-cat-831` و `gsp-cat-878` به فهرست ممنوعیت روش محلی افزوده شدند؛ ممنوعیت قدیمی حفظ شد. تغییر از API مجاز تنظیمات، با همان مقصد بانکی و سایر مقادیر انجام شد.

۱۵ سناریو با تنظیمات واقعی مقصد و داده ساختگی فقط در حافظه موفق شدند: کمتر/برابر/بیشتر از سقف‌ها، هر سه شاخه طلا، فرزند هر شاخه و سبد مخلوط. سفارش/کاربر/آدرس/ارسال ساختگی این probeها در دیتابیس مقصد نوشته نشد.

## محدودیت‌های باقی‌مانده

قیمت و موجودی snapshot هستند؛ موتور زنده طلا/اعتبار/کمپین مبدأ وارد نشده است. متن و SEO عمومی مبدأ حفظ شده‌اند و ممکن است نام گوشی‌شاپ داشته باشند؛ ویرایش محتوای برند پیش از استفاده عمومی جداست. اسلات ظرفیت‌دار، خبرم‌کن، سرویس کامل نظر و پرسش‌وپاسخ با import ساخته نشده‌اند. داده‌های قدیمی آزمون، به درخواست حفظ اطلاعات، کنار داده جدید باقی مانده‌اند. ارسال و اطلاعات بانکی مقصد حفظ شده‌اند و تنظیم عملیاتی هر فروشنده/پوشش ارسال باید پیش از فروش واقعی بررسی شود. این اجرا اتصال یا تراکنش واقعی درگاه، انتشار Liara یا پذیرش مجوز نیست.
