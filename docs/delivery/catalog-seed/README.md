# بسته داده تست کاتالوگ — ۲۲ نوامبر ۲۰۲۶

[فایل واحد JSON](../../../data/catalog/gooshishop-2026-11-22.json) داده عمومی کاتالوگ مبدأ را به ساختار فعلی چریوا نگاشت می‌کند. SQL Server مبدأ فقط با `SELECT` خوانده شد. اتصال، رمز، مشتری، حساب کاربری، سفارش، اطلاعات بانکی، تسویه و دفتر مالی مبدأ داخل بسته نیستند.

این تحویل **آماده ورود** است؛ داده به دیتابیس بررسی فعلی الیاس یا دیتابیس سرور وارد نشده است. آزمایش ورود روی schema موقت PostgreSQL انجام و پس از آزمون حذف شد.

## نگاشت فیلدها

- دسته: نام فارسی/انگلیسی، توضیح، انتشار، والد، آیکن، SEO، اتصال خصوصیات و ویژگی کارت/فیلتر.
- برند: نام، فعال‌بودن و آیکن؛ نام انگلیسی، توضیح و SEO که مدل فعلی برند ندارد، در `source_records.brands` حفظ شده‌اند.
- محصول: نام فارسی/انگلیسی، توضیح کوتاه و کامل، مزایا/معایب، دسته اصلی، برند اصلی، تصاویر، ویژگی‌ها، وضعیت، تاریخ ایجاد، SEO، noindex/nofollow، اجازه نظر و وزن/ابعاد حمل.
- تنوع: رنگ/گارانتی برای دیجیتال؛ وزن/گارانتی برای دسته‌های طلا. مقدار ثبت‌نشده صریحاً «نامشخص در مبدأ» است و با «بدون گارانتی» جایگزین نشده است. تنوع‌های همسان در مدل دو محور یکی می‌شوند و نگاشت PACهای اصلی در فایل می‌ماند.
- عرضه: فروشنده فعال، تعداد موجود، قیمت، قیمت قبل از تخفیف و اتصال محصول/تنوع. ترکیب تکراری فروشنده/تنوع با کمترین قیمت انتخاب و موجودی‌ها جمع نمی‌شوند.
- قیمت: واحد مبدأ و مقصد **تومان (`IRT`)** است. برای فروشنده منتخب، `PAC.FinalPrice`؛ برای سایر فروشنده‌ها، قیمت نقدی همان `SPAC.OverriddenPrice`. موتور تخفیف، اقساط و کمپین مبدأ دوباره محاسبه نشده است. اعداد اعشاری احتمالی به نزدیک‌ترین تومان با نیم به بالا گرد می‌شوند.
- قیمت خط‌خورده فقط اگر از قیمت نقدی بیشتر و بازه اعتبارش فعال باشد منتقل می‌شود؛ اختلاف معتبر قیمت پایه و `FinalPrice` نیز حفظ می‌شود. ۷۵۶ عرضه این شرایط را دارند.
- وزن حمل در کد مبدأ گرم است؛ ابعاد با توجه به `SyncProductDimensionsTask` سانتی‌مترند و برای مدل فعلی به میلی‌متر تبدیل شده‌اند. صفر به‌معنی نامعلوم است و حذف می‌شود. وزن طلای محور تنوع، وزن حمل نیست.
- وقفه ثابت فروشنده: بیشینه وقفه پروفایل تأمین‌کننده پس از تبدیل به روز و مهلت‌های عرضه‌های منتخب؛ جزئیات اصلی حفظ شده‌اند. نام مالک، شهر یا تعهد تجاری نامعلوم حدس زده نشده‌اند.
- پرچم مستقل پرسش‌وپاسخ در Product مبدأ وجود ندارد؛ `qa_enabled=false`. سرویس کامل نظر/پرسش‌وپاسخ با واردکردن داده ساخته نمی‌شود.

`source_records` متن کامل و فیلدهای عمومیِ اضافی، مشخصات گروه‌بندی‌شده، تصاویر بیشتر از سقف گالری، انتساب‌های ثانویه دسته/برند، قیمت‌های اقساطی، پروفایل و نرخ پایه طلا را نگه می‌دارد. نرخ `PriceInRial` در همان بخش با نام و واحد اصلی باقی می‌ماند؛ به قیمت تومانی عرضه تبدیل یا به موتور طلا تزریق نشده است. مدل قیمت فعلی چریوا همان قیمت نهایی ثابت است.

محدودیت‌های فعلی مدل، مثل گالری، طول متن و مزایا/معایب، روی نگاشت نمایشی رعایت شده‌اند. ۳۴ تعدیل در `projection_adjustments` ثبت شده؛ اصل متن در بخش مبدأ حفظ است. HTML واردشده با همان سیاست ویرایشگر محصول چریوا پاک‌سازی می‌شود.

## تصاویر و بنرها

JSON شامل URL عمومی، مشخصات و SHA-256 تصاویر است؛ باینری تصاویر داخل فایل ۵۰ مگابایتی تکرار نشده است. تمام ۱۰۴۹۵ لینک انتخاب اولیه بررسی شدند: هیچ تصویر اصلی محصول خراب نبود؛ ۴۳۷ تصویر فرعی/آیکن خطای۴۰۴ داشت. آن‌ها از نگاشت نمایشی حذف و در `media_verification.unavailable_optional` و `source_records.media_references` حفظ شدند. آیکن ناموجود از پیش‌فرض رابط استفاده می‌کند.

برای اولین ورود، CDN مبدأ باید از دستگاه اجرا قابل دسترسی باشد. ابزار تصویر را دریافت، checksum را بررسی، کامل decode و مانند آپلود فعلی به PNG حداکثر۱۰۲۴ پیکسل تبدیل می‌کند. پس از ورود، تصاویر از دیتابیس مقصد و مسیر `/catalog/icons/{id}` ارائه می‌شوند؛ نمایش سایت به CDN مبدأ وابسته نیست. دسترسی تصویر همچنان در سرویس برنامه بررسی می‌شود.

برای این حجم، migration `000004-catalog-media` باینری را در جدول `catalog_media` نگه می‌دارد؛ JSON workspace فقط مرجع دارد. ورودی قدیمیِ inline همچنان خوانده می‌شود و در اولین نوشتن عادی، داخل همان تراکنش به جدول منتقل می‌شود. گالری/آیکن بدون مرجع جمع‌آوری می‌شود. ورود از فایل‌های cache به‌صورت تدریجی داخل یک تراکنش انجام می‌شود؛ همه تصاویر یکجا در RAM نگه داشته نمی‌شوند.

بنرهای گوشی‌شاپ، متن کمپین و لینک‌های قدیمی فقط در `source_records.homepage` آرشیو شده‌اند؛ به‌صورت خودکار بنر فعال چریوا نمی‌شوند. بنرهای چریوا و هویت A/C فعلی از تنظیمات خود چریوا می‌آیند. تنظیمات حساب بانکی، ارسال، جغرافیا و پرداخت مبدأ کپی نمی‌شوند؛ در مقصد توسط تیم تنظیم می‌شوند.

## ورود محلی

ابزار در `apps/api/cmd/catalog-import` است. پیش‌فرض، **اعتبارسنجی بدون اتصال/نوشتن دیتابیس** است:

```powershell
Set-Location D:\Cherriva\apps\api
go run ./cmd/catalog-import -file ../../data/catalog/gooshishop-2026-11-22.json
```

برای بررسی فایل‌های تصویر بدون نوشتن دیتابیس:

```powershell
go run ./cmd/catalog-import -file ../../data/catalog/gooshishop-2026-11-22.json -verify-media -cache "$env:USERPROFILE\.codex\local-runtimes\cherriva\catalog-export\media-cache"
```

پس از دریافت دستور ورود داده، اتصال **فقط دیتابیس بررسی مقصد** را در `REVIEW_DATABASE_URL` همان نشست تنظیم کنید. روی سیستم فعلی از همان اتصال خصوصی راه‌انداز لوکال استفاده می‌شود؛ نیازی به رمز SQL Server مبدأ نیست. متغیر `DATABASE_URL` هم‌زمان تنظیم نباشد. ابتدا برنامه مقصد باید workspace را ایجاد کرده باشد. راه‌انداز `Start-Cherriva` migrationها را اجرا می‌کند؛ برای اجرای دستی:

```powershell
go run ./cmd/migrate -dir ../../db/migrations
go run ./cmd/catalog-import -file ../../data/catalog/gooshishop-2026-11-22.json -mode review -apply -configure-home -cache "$env:USERPROFILE\.codex\local-runtimes\cherriva\catalog-export\media-cache"
```

`-configure-home` فقط نگاشت چهار ریل را تغییر می‌دهد؛ بنرها و تنظیمات مالی/حمل دست‌نخورده می‌مانند. حذف این flag، نگاشت موجود خانه را هم حفظ می‌کند. `-limit-products 20` فقط برای نمونه‌گیری روی **دیتابیس موقت مستقل** است؛ برای تحویل کامل استفاده نشود. نمونه و فایل کامل را پشت‌سرهم در یک مقصد نریزید، چون شناسه‌های مشترک عمداً conflict می‌شوند.

پس از ورود، قواعد وابسته به شناسه دسته باید برای شناسه‌های تازه بررسی شوند. در همین فایل، محصولات طلای موجود در `gsp-cat-828` (سکه)، `gsp-cat-831` (شمش) و `gsp-cat-878` (آب‌شده) هستند؛ محدودیت پرداخت محلی باید این دسته‌ها و زیرشاخه‌هایشان را هم پوشش دهد. محدودیت‌های کارت‌به‌کارت۱۵میلیون و محلی۳۰میلیون برای کل سفارش و قاعده سبد مخلوط هم در تست مقصد بررسی شوند. importer عمداً تنظیمات مالی موجود را عوض نمی‌کند؛ نگاشت این شناسه‌ها باید در تنظیمات مقصد تکمیل شود، بدون تغییر دفتر مالی یا مشخصات بانکی. تا آن زمان، ورود موفق کاتالوگ به‌معنی آماده‌بودن checkout برای فروش عمومی نیست.

شناسه‌ها namespace ثابت `gsp-` دارند. شناسه تکراری موجود بازنویسی نمی‌شود؛ کل ورود rollback می‌شود. تکرار دقیق همان ورود، بدون رکورد و audit تکراری، `already_applied=true` برمی‌گرداند. تغییر موجودی/قیمت بعد از ورود، با retry به مقادیر snapshot برنمی‌گردد. هیچ endpoint عمومی برای import اضافه نشده است.

## ورود روی سرور توسط پارسا

در image ساخته‌شده از این تغییر، `catalog-import` کنار `server` و `migrate` وجود دارد. JSON عمداً داخل image نیست. فایل و SHA را از همین revision دریافت و به فضای موقت/volume مناسب انتقال دهید. در shell محیط مقصد با `DATABASE_URL` موجود و بدون `REVIEW_DATABASE_URL`:

```sh
migrate -dir /app/migrations
catalog-import -file /tmp/gooshishop-2026-11-22.json -mode live
catalog-import -file /tmp/gooshishop-2026-11-22.json -mode live -apply -configure-home -workers 1 -cache /tmp/cherriva-catalog-media
```

`live` به data-origin دیتابیس عملیاتی اشاره دارد؛ داده همچنان snapshot تست است. workspace مقصد باید قبلاً با اجرای برنامه ایجاد شده باشد. ابزار اختلاف origin را رد می‌کند و حساب ادمین یا ورود آزمون نمی‌سازد. بانک/ارسال/شهر و مجوزهای مقصد را جدا تنظیم کنید. قیمت و موجودی این فایل snapshot زمان استخراج‌اند؛ به‌روزرسانی زنده یا وعده فروش واقعی نیستند.

اصل تصاویر معتبر حدود ۴۹۲ مگابایت و PNGهای تبدیل‌شده جمعاً ۳٬۳۴۹٬۳۸۷٬۲۸۹ بایت (حدود۳٫۱۲GiB) هستند. فضای cache شامل هر دو است؛ فضای PostgreSQL، WAL و backup هم جدا لازم است. برای container کوچک، `-workers 1` فشار حافظه decode را کم می‌کند. برای ورود کامل، فضای دیسک cache و PostgreSQL را مطابق آن آماده کنید. اگر تصویر در CDN عوض شده باشد، checksum مانع جایگزینی بی‌سروصدا می‌شود؛ snapshot باید آگاهانه تازه شود. داده را به‌جای overwrite کل workspace، فقط با همین importer وارد کنید.
