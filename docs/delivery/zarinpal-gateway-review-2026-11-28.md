# بررسی پیش از اجرای درگاه زرین‌پال

[اصلاح انتخاب‌شده پس از بازبینی #153](payment-settings-revision-2026-11-28.md) تنظیمات OAuth را از پرداخت V4 جدا کرد، شرح را از تنظیمات برداشت و فرم را به فهرست ثابت با سوییچ و بخش‌های بسته تبدیل کرد. متن اولیه پایین سابقه تحلیل است؛ مرحله اتصال مالی هنوز شروع نشده است.

**تکمیل بعدی مالک:** ابتدا فقط تنظیمات ساخته و برای بررسی دستی تحویل شود؛ [قدم تنظیمات #152](payment-gateway-settings-2026-11-28.md) با retry و اجازه شارژ و credential اختصاصی پیاده شد. مسیر بازگشت از فرم حذف و از مسیر ثابت کد و origin محیطی ساخته می‌شود. اجرای adapter/پرداخت هنوز شروع نشده است؛ وضعیت not-started بالا به اتصال مالی اشاره دارد و متن بررسی اولیه پایین سابقه تحلیل است.

## مسئله، دامنه و خواسته صریح

مالک زرین‌پال را نخستین درگاه برای آماده‌سازی اتصال معرفی کرد؛ قرارداد تجاری هنوز قطعی نیست. تنظیمات هر درگاه باید کنار روش‌های فعلی در تنظیمات خرید/پرداخت باشد و فقط فیلدهای اختصاصی همان ارائه‌دهنده را نشان دهد. نمونه username/password/client-id/client-secret یا API-key الزام همه درگاه‌ها نیست. درخواست این نوبت «اول بررسی کن» است؛ این سند نتیجه بررسی و طراحی پیشنهادی است و کد اجرایی یا اتصال مالی جدید ایجاد نمی‌کند.

پیش‌شرط‌ها: [نقش‌ها](../product/roles.md)، [مرز شارژ و مصرف](../decisions/adr-001-pricing-and-payment-boundaries.md)، [قواعد پرداخت](../domains/payments/README.md)، [قرارداد جاری سفارش](../architecture/contracts/order-lifecycle.md) و [منابع اعتبار](../architecture/contracts/wallet-credit-policy.md). مقصد این اتصال بک‌آفیس و سایت مشتری است؛ تنظیمات پذیرنده متعلق به مدیریت سایت است، نه هر فروشگاه.

## طراحی پیشنهادی تنظیمات

در همان تب پرداخت و کنار کارت‌های موجود، «افزودن درگاه» با انتخاب ارائه‌دهنده از فهرست درگاه‌های پیاده‌شده قرار بگیرد. تنظیم عمومی شامل نام، فعال‌بودن، حداقل/حداکثر، دسته‌های مجاز/مستثنا و راهنما حفظ شود؛ ارتباط فعلی با روش فروش هم حفظ شود. kind و provider از شناسه رکورد اتصال جدا باشند تا نوع درگاه با ID اشتباه نشود.

فرم از schema تعریف‌شده در سرور برای هر provider ساخته شود؛ فیلدهای اجباری، نوع عدد/انتخاب/متن/محرمانه و validation همان provider را داشته باشد. این سازوکار ساخت فرم را مشترک می‌کند؛ پروتکل هر درگاه همچنان adapter مشخص خودش را لازم دارد و با چند credential دلخواه پشتیبانی نمی‌شود.

| فیلد زرین‌پال | پیشنهاد نمایش / رفتار |
| --- | --- |
| merchant-id | شناسه پذیرنده با قالب UUID؛ برای Sandbox ساختگی. خواندن عمومی آن لازم نیست. |
| محیط | dropdown «آزمایشی / واقعی»، پیش‌فرض پیشنهادی آزمایشی؛ Sandbox مجاز به شارژ دفتر واقعی نیست. |
| base-url | آدرس رسمی از محیط پر شود؛ اگر override لازم شد فقط با اعتبارسنجی میزبان/HTTPS و مجوز مدیریت، برای جلوگیری از ارسال credential به مقصد دلخواه. |
| callback | فیلد تنظیمات نیست؛ طبق اصلاح صریح مالک، مسیر متعلق به کد و origin از `PAYMENT_PUBLIC_BASE_URL` محیط است. مقدار کاربر یا Host درخواست مبنا نباشد. |
| واحد | پیشنهاد نسخه اول IRR صریح و فقط‌خواندنی؛ نمایش تومان در محصول حفظ شود. |
| توضیح تراکنش | الگوی کوتاه برای شارژ مستقل/شماره سفارش؛ داده حساس یا متن نامحدود وارد آن نشود. |
| auto-verify | گزینه پیشرفته مطابق مستندات؛ پیشنهاد آغاز، verify تحت کنترل سرور با بازیابی. مقدار نهایی و مهلت عملیاتی در GATEWAY-Q03 تعیین شود. |

برای providerهای بعدی فقط فیلدهای مستند همان درگاه اضافه شوند. secretها نوشتنی، رمزنگاری‌شده با کلید خارج دیتابیس و دارای وضعیت «تنظیم شده» باشند؛ API خواندن، audit، لاگ، export، snapshot سفارش و storefront مقدار خام را دریافت نکنند. خالی‌ماندن فیلد در ویرایش نباید credential قبلی را ناخواسته پاک کند؛ تعویض/حذف صریح باشد. کنترل تغییر با مجوز مدیریت پرداخت و نسخه تنظیمات است. تغییر merchant یا محیط نباید verify تلاش‌های قبلی را به اتصال جدید ببرد؛ نسخه اتصال لازم است.

ذخیره draft بدون credential واقعی ممکن باشد، اما فعال‌شدن واقعی نیازمند تنظیم کامل و شرایط پذیرنده است. تست داخلی با سرویس ساختگی از تست زنده Sandbox و هر دو از پرداخت واقعی جدا گزارش شوند.

## مسیر پیشنهادی پرداخت

1. ثبت سفارش/مرسوله طبق مسیر موجود؛ ایجاد تلاش شارژ با مبلغ و واحد ثابت در سرور و اتصال به مشتری/خرید.
2. request از adapter زرین‌پال، ثبت Authority و سپس هدایت مشتری؛ درخواست تکراری تلاش تأییدشده یا وجه دوم نسازد.
3. callback با correlation پایدار به همان تلاش، بدون وابستگی به نشست مرورگر؛ Status یا مبلغ query مبنای شارژ نشود.
4. verify از سرور با merchant/محیط نسخه همان تلاش، مبلغ ثابت و Authority؛ ثبت مرجع یکتا و credit دقیقاً یک بار با حفظ منشأ وجه.
5. پیشنهاد GATEWAY-Q01: برای سفارش معتبر، debit مستقل کیف پول و پرداخت سفارش خودکار انجام شود؛ شروع processing همچنان اقدام ادمین/فروشگاه باشد. شارژ مستقل فقط کیف پول را افزایش دهد.
6. نتیجه دیررس پس از انقضای رزرو، فقط شارژ را ثبت کند؛ خرید منقضی خودکار احیا نشود و شرایط تازه تأیید شود.

## نتیجه بررسی

بازبینی سورس و مستندات انجام شد؛ تست محصول یا فراخوانی request/verify زنده اجرا نشد. سرویس محلی، credential، دیتابیس، دفتر مالی و سفارش‌ها تغییر نکردند. برنامه فنی برای شروع با محیط ساختگی/Sandbox قابل آماده‌سازی است؛ فعال‌سازی تجاری بعد از تکمیل موارد باز انجام می‌شود.
