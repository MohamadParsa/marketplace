# برنامه کامل پیاده‌سازی Marketplace

**بازنگری دامنه لازم پس از پاسخ #13:** [ADR-005](../decisions/adr-005-review-v1-1-product-responses.md) و [اثر بر backlog](analysis-backlog.md#issue-13-scope) مرجع تغییر هستند. بخش‌های پایین که نقش ثابت/یک مالک را نسخه اول می‌دانستند، برنامه نسخه آزمون قبلی‌اند؛ دامنه جدید admin، نقش قابل تعریف و عضویت چندبه‌چند دارد. شرح‌های فعال و وابستگی پس از #14 در [فهرست جاری](review-v1-1/README.md) آمده‌اند؛ بخش‌های قدیمی این رودمپ شاهد دامنه/اجرای جدید نیستند. CMS و زیرسایت‌ها الزام شروع نیستند.


## ۱. اصول اجرایی

پیاده‌سازی در سه تحویل اصلی انجام می‌شود:

1. بک‌آفیس
2. پنل فروشندگان
3. سایت مشتری

ترتیب داخل هر تحویل نیز مرحله‌ای است. هر مرحله باید توسعه، تست، داده آزمون، مستندات و معیار پذیرش خودش را کامل کند؛ سپس مرحله بعد شروع می‌شود.

قواعد ثابت:

- backend مشترک در `apps/api` به شکل modular monolith ساخته می‌شود.
- رابط‌ها مستقل هستند:
  - `apps/backoffice-web`
  - `apps/seller-portal-web`
  - `apps/storefront-web`
- قراردادهای API در `packages/contracts` نگهداری می‌شوند.
- قواعد مالی، سفارش و دسترسی در backend مرجع هستند.
- مبلغ داخلی و مرز درگاه ریال است؛ نمایش رابط تومان است.
- تاریخ و تقویم کسب‌وکار بر اساس `Asia/Tehran` و نمایش شمسی است.
- اتصال واقعی پرداخت، پیامک و حمل در مرحله اول انجام نمی‌شود؛ آداپتر آزمایشی استفاده می‌شود.
- داده‌های آزمون ساختگی و قابل reset هستند.
- هیچ پرسش مسدودکننده با حدس پیاده‌سازی نمی‌شود.

# ۲. مرحله صفر: آماده‌سازی مشترک

این مرحله محیط اجرایی را آماده می‌کند و محصول قابل استفاده کاربر نهایی تولید نمی‌کند.

## ۲.۱ ساختار پروژه

- ایجاد workspaceهای frontend و backend.
- ایجاد package قراردادها.
- تنظیم TypeScript، Go، lint، format و build.
- تعریف محیط‌های local، test و staging.
- تعریف مدیریت secret بدون قرار دادن مقدار واقعی در repository.
- تعریف pipeline بررسی build، test و migration.

## ۲.۲ هویت و نشست

### بک‌آفیس

- ورود با شماره و رمزعبور.
- خروج از حساب.
- بازنشانی رمزعبور.
- انقضای نشست.
- ابطال نشست‌های قبلی پس از تغییر رمز.
- محدودیت تلاش ناموفق.
- ثبت ورود موفق و ناموفق.
- ثبت IP و device metadata در حد مورد نیاز امنیتی.

### فروشنده

- ورود طبق [قواعد هویت واحد](../domains/identity/README.md).
- اعتبار OTP نود ثانیه.
- حداکثر پنج تلاش در یک ساعت.
- ارسال مجدد پس از شصت ثانیه.
- تغییر شماره فقط پس از احراز هویت مجدد.

### مشتری

- ورود نخست با موبایل و OTP. ورود بعدی با موبایل یا ایمیل و رمز پس از تنظیم آن.
- ادغام سبد مهمان و کاربر.
- خروج کامل و پاک‌سازی داده خصوصی از حافظه سمت کاربر.

## ۲.۳ مجوز و مالکیت داده

- middleware احراز هویت.
- middleware مجوز.
- فیلتر مالکیت فروشگاه.
- فیلتر مالکیت مشتری.
- کنترل مرحله‌ای دسترسی به اطلاعات سفارش.
- جلوگیری از نشت داده در:
  - API
  - export
  - log
  - cache
  - پیامک
  - جست‌وجو
- تعریف کد خطا برای دسترسی غیرمجاز، منبع ناموجود و وضعیت نامعتبر.

## ۲.۴ قراردادهای مشترک

برای همه APIها مشخص شود:

- شکل pagination.
- فیلتر و مرتب‌سازی.
- validation.
- فرمت تاریخ.
- واحد مبلغ.
- کد خطا.
- correlation id.
- idempotency key.
- optimistic locking یا نسخه رکورد.
- فرمت audit event.
- وضعیت‌های loading، empty، error و partial success.

## ۲.۵ داده آزمون

داده seed باید حداقل شامل این موارد باشد:

- چند کاربر بک‌آفیس با نقش‌های مختلف.
- چند فروشگاه فعال و غیرفعال.
- محصول مستقل و مشترک.
- چند دسته و خصوصیت.
- چند پیشنهاد فروشگاه.
- کالا با موجودی کم.
- خرید چندفروشگاهی.
- سفارش دارای عدم تأمین.
- پرونده تأمین جایگزین.
- بسته چندگانه.
- پرداخت موفق، ناموفق و نامشخص.
- refund.
- تسویه قبلی و بدهی پس از refund.
- برداشت در انتظار، ردشده و شکست‌خورده.
- داده‌های محدودشده برای بررسی مجوز.

- مشاهده تاریخچه تغییرات.
- خروج‌دادن کاربر از نشست‌های فعال.
- جلوگیری از حذف تنها ادمین فعال.
- ثبت actor، زمان، هدف و نوع تغییر در audit.

### صفحات

تاریخ ثبت: ۲۰۲۶-۱۱-۱۰

| بخش | وضعیت | شواهد |
| --- | --- | --- |
| workspaceهای سه محیط و backend | انجام‌شده به‌صورت اسکلت | `apps/api/`، `apps/backoffice-web/`، `apps/seller-portal-web/`، `apps/storefront-web/` |
