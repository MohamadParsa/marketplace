# ساختار codebase و معماری اجرایی اولیه

- نوع: معماری
- تاریخ تصمیم: 2026-11-09
- اسناد و پرسش‌های متأثر: [معماری منطقی](../architecture/README.md)، [آمادگی برای پیاده‌سازی](../delivery/readiness.md)

## زمینه و مسئله

محصول سه محیط کاربری دارد: بک‌آفیس، پنل فروشنده و سایت مشتری. لازم است کدها قراردادها و قواعد مشترک را دوباره‌نویسی نکنند، اما هر محیط بتواند مستقل build و deploy شود. همچنین backend باید مرزهای دامنه‌ای روشن و قابلیت تست مناسب داشته باشد.

## گزینه‌ها

| گزینه | مزایا | هزینه / محدودیت | دلیل انتخاب یا رد |
| --- | --- | --- | --- |
| یک repository برای هر محیط | استقلال repository و انتشار | تکرار قرارداد، type و UI؛ هماهنگی دشوار | رد شد |
| چند microservice از روز اول | استقلال استقرار و مقیاس‌گذاری | پیچیدگی عملیاتی، تراکنش و مشاهده‌پذیری زودهنگام | رد شد |
| monorepo با modular monolith | اشتراک کنترل‌شده و مرزهای روشن با پیچیدگی عملیاتی کمتر | نیازمند نظم در وابستگی ماژول‌ها | انتخاب شد |

## تصمیم

- repository و ریشه کاری پروژه `marketplace` است و مستندات و کد در همین repository نگهداری می‌شوند.
- کل marketplace در یک monorepo نگهداری می‌شود:
  - `apps/api` برای backend مشترک
  - `apps/backoffice-web`، `apps/seller-portal-web` و `apps/storefront-web` برای محیط‌های کاربری مستقل
  - `packages/` برای قراردادها، UI و تنظیمات مشترک
  - `db/migrations` برای migrationهای versioned دیتابیس
- backend با Go و به‌صورت modular monolith ساخته می‌شود.
- Hexagonal Architecture در سطح هر ماژول دامنه استفاده می‌شود؛ domain و application به adapterهای HTTP، دیتابیس یا ارائه‌دهنده بیرونی وابسته نیستند.
- stack اولیه بک‌آفیس React + TypeScript + Vite است، همراه با TanStack Query، React Router، React Hook Form، Zod و MUI. انتخاب stack سایت مشتری می‌تواند جداگانه و بر اساس نیاز SEO/SSR انجام شود.
- پلتفرم استقرار اولیه Liara است؛ جزئیات اجرایی آن در [ADR-003](adr-003-liara-deployment.md) ثبت شده است. ابزار migration هنوز انتخاب نشده است.

## پیامدها

- انتشار هر frontend می‌تواند مستقل باشد، بدون جداکردن repositoryها.
- قواعد دامنه در backend مرجع باقی می‌مانند و frontend مبلغ یا وضعیت مالی را تعیین نمی‌کند.
- قراردادهای API باید در `packages/contracts` یا schema مرجع نگهداری شوند و client فرانت از آن تولید/به‌روزرسانی شود.
- هر migration پس از اجرا immutable است و با شماره نسخه و فایل برگشت‌پذیر در `db/migrations` ثبت می‌شود.
- استخراج یک ماژول به سرویس مستقل فقط پس از وجود نیاز واقعی عملیاتی یا مقیاس‌پذیری بررسی می‌شود.

## اعمال تصمیم

ساختار repository، قراردادها و معیار آمادگی هر برش باید با این تصمیم سازگار باشند. این ADR جایگزین قواعد حوزه‌ها نیست؛ مالکیت قواعد همچنان در اسناد `docs/domains/` باقی می‌ماند.

## بازنگری یا جایگزینی

در صورت نیاز به چرخه انتشار مستقل، مقیاس‌گذاری جداگانه یا مرز عملیاتی مستقل برای یک ماژول، ADR جداگانه برای استخراج آن سرویس ثبت شود.
