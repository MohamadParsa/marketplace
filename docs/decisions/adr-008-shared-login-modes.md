# روش ورود مشترک سایت و بک‌آفیس

## تصمیم صریح مالک

در ادامه اجرای #27، مالک انتخاب نهایی را برای **هر دو محیط بک‌آفیس و سایت مشتری** مشخص کرد:

| شناسه ورود | مسیر |
| --- | --- |
| ایمیل متصل به حساب | فقط رمز عبور؛ OTP ایمیلی برای ورود اضافه نمی‌شود |
| شماره موبایل | ابتدا ورود شماره، سپس انتخاب رمز عبور یا OTP موبایل؛ انتخاب رمز نباید به‌خودی‌خود پیامک بفرستد |
| ایجاد حساب مشتری | نخست تأیید موبایل با OTP؛ ایمیل اختیاری و رمز بعداً در پروفایل همان User ثبت می‌شوند |

پاسخ گذرای «OTP به ایمیل تأییدشده» با اصلاح صریح بعدی مالک جایگزین شد و مجوز پیاده‌سازی مسیر ایمیلی نیست. بخش قدیمی ADR-005 که شروع تمام ورودها را فقط موبایل می‌دانست، در همین موضوع با تصمیم جاری تکمیل شده است؛ قواعد دیگر آن ADR پابرجا هستند. ایمیل اختیاری/یکتا و هویت مشترک تغییر نکرده‌اند. حساب بدون رمز نمی‌تواند از ورود با رمز نشست بگیرد؛ مسیر OTP موبایل همچنان در دسترس اوست.

## اثر فنی و دامنه تحویل

API رمز، شماره نرمال‌شده یا ایمیل نرمال‌شده را با همان اعتبارنامه حساب بررسی می‌کند؛ OTP ورود فقط شماره معتبر می‌پذیرد و ایمیل در آن رد می‌شود. رابط بک‌آفیس در اجرای جاری #27 همراه با پروفایل تعریف رمز و ایمیل ساخته می‌شود؛ رابط ورود مشتری در #30 همین قاعده را مصرف می‌کند. وجود API مشتری به معنی تکمیل UI خرید یا آماده‌بودن اتصال پیامک واقعی نیست.

ایمیل/هش رمز در مخزن PostgreSQL آزمون با migration جدا پایدار می‌شوند؛ hash در API یا لاگ برنمی‌گردد. محدودیت تلاش رمز و اندازه ورودی کنترل فنی این برش‌اند؛ نشست و OTP آزمون حافظه‌ای‌اند و پذیرش production جداست. سیاست تأیید ایمیل برای بازیابی، تغییر موبایل و ارسال واقعی از این تصمیم نتیجه نمی‌شوند.
