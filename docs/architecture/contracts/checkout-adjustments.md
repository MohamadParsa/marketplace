# قرارداد اجرای #67، #68، #69 و #78

دستور «چهار مورد را انجام بده» مجوز اجرای این چهار قابلیت است؛ دستور نگه‌داشت تغییرات لوکال پابرجاست. این سند از [طراحی #66](checkout-amounts-usage.md) استفاده می‌کند و تصمیم‌های تازه مالک را ثبت می‌کند؛ تأیید کل سند یا تکمیل #70/#72/#73/#79 از آن نتیجه نمی‌شود. [گزارش و شواهد](../../delivery/next-phase/issues-67-68-69-78-verification.md).

## دامنه اجرایی و مرز وابستگی‌ها

روش‌های فعلی نقدی و مارکاپشان صفر است. `Offer.Price` نقدی نهایی پس از تخفیف مستقیم است؛ `RegularPrice` دوباره کسر نمی‌شود. این چهار کار موتور طلا/کمیسیون/لندتک و تنظیم روش فروش #72/#73 را فعال نمی‌کنند. آزمون مستقل Money، مثال۹۳۶ را پوشش می‌دهد؛ اتصال مارکاپ واقعی به همین مبنا وظیفه #73 است، نه ادعای قابلیت فعال فعلی.

زیرساخت ضروری #70 در حد همین روش‌های فعلی اجرا می‌شود: رزرو موجودی/سهمیه/اعتبار و ثبت purchase در یک `Repository.Update`؛ تأیید وجه و تأیید سفارش جدا. تحلیل جامع PlaceOrder، retry ارائه‌دهندگان بیرونی و دامنه شکست‌های آینده #70 باز می‌ماند. برای #78 نگاشت مقادیر در کتابخانه مشترک کافی است؛ گسترش گروه‌بندی به تمام فیلترهای PLP و سایر کاربردهای #79 در این تحویل نیست.

## پول و snapshot

Amount داخلی ریال صحیح؛ API مبلغ تومان decimal string با حداکثر یک اعشار. نرخ کوپن basis point صحیح، حداکثر۱۰۰٪؛ گردکردن نیم‌به‌بالا تا ریال. مبلغ ثابت با largest remainder و کلید پایدار واحد `item:<offer>:<ordinal>` یا `shipping:<store>` توزیع می‌شود. سهم هزینه پلتفرم یک بار محاسبه و میان همان تخصیص‌ها پخش می‌شود؛ جمع سهم پلتفرم و سلر دقیقاً مبلغ تخفیف است.

Quote نسخه۲، `DiscountUsage` شامل نسخه کامل قانون و تخصیص واحد/ارسال دارد. `CreditUsage` شامل اعتبار انتخابی، تخصیص منابع قبلی/وجه جدید و وضعیت held/posted/released است. این‌ها کنار Quote/Purchase در payload پایدار workspace هستند؛ جدول دفتر فعلی تغییر نمی‌کند. لغو کامل مبلغ همین snapshot را به کیف پول برمی‌گرداند. تخصیص واحدها برای لغو جزئی آینده محفوظ است؛ UI/عملیات جدید لغو جزئی در این چهار کار ساخته نشده است.

## سازگاری و منشأ اعتبار

Quote بدون `contract_version` نسخه قبلی باقی می‌ماند؛ داده قدیمی بازنویسی نمی‌شود. سایت جدید `contract_version:2` می‌فرستد. فیلد کوپن/اعتبار غیرصفر روی قرارداد قدیمی پذیرفته نمی‌شود. سفارش قدیمی همچنان قابل بررسی است، ولی writer قدیمی نیز نمی‌تواند اعتبار رزروشده خرید جدید را خرج کند.

در اولین پذیرش نسخه۲ برای یک کاربر، مانده فعلی دفتر به lot با منشأ صریح `legacy-unattributed` و anchor هش تاریخچه موجود تبدیل می‌شود؛ **فقط metadata است و credit مالی تازه‌ای نیست**. واریزهای بعدی lot مستقل با مرجع ledger دارند. مصرف معمولی از منابع آزاد FIFO و مصرف خرید نسخه۲ از تخصیص دقیق همان خرید است. دفتر فقط یک `order-payment` دارد؛ usage برداشت موازی نمی‌سازد. بازپرداخت قبلی و hold آن هم محفوظ‌اند.

تأیید واریز فعال، فقط بخش موردنیاز از lot همان واریز را به خرید اختصاص می‌دهد؛ مبلغ اضافه آزاد است. بعد از انقضا credit آزاد می‌ماند و نیاز به quote تازه است. لغو/انقضا سهم held را آزاد می‌کند؛ تأیید خرید تنها با جمع تخصیص دقیقاً برابر کل سفارش انجام می‌شود.

## API و مجوز

- `GET /backoffice/commerce/coupons`: فهرست و تعداد رزرو/مصرف و مجوزهای مؤثر.
- `POST /backoffice/commerce/coupons`: ساخت/ویرایش نسخه‌دار، کلید idempotency؛ مجوز create/edit و برای تغییر active مجوز activate نیز لازم است.
- `POST /backoffice/commerce/coupons/activate`: فعال‌سازی مستقل با version و کلید؛ مجوز activate.
- `POST /backoffice/commerce/coupons/preview`: پیش‌نمایش قانون ذخیره‌شده روی عرضه/تعداد/هزینه ارسال نمونه؛ فعال بودن نادیده گرفته می‌شود، تاریخ/بازه/سهمیه برقرارند؛ هیچ رزرو/مصرفی ندارد.
- مجوزهای قابل انتساب: `commerce.coupons.read/create/edit/activate` و برای نگاشت مستقل `attribute.groups.set`. عملیات، مدیریت و مالی طبق نقش موجود و کنترل سرور؛ فروشنده به این endpoint دسترسی ندارد.
- ورودی checkout نسخه۲: `coupon_code` و `wallet_toman` در کنار آدرس، ارسال و روش تأمین. خروجی: `discount_toman`، `wallet_selected_toman`، `funding_toman`، کل مبلغ و `terms_digest`.
- پذیرش نسخه۲ به digest و مبلغ همان quote نیاز دارد؛ تغییر قانون/قیمت/موجودی/محدودیت/اعتبار یا رضایت قدیمی رد می‌شود. پذیرش تکراری همان کلید دوباره رزرو نمی‌کند.
- خطا: ۴۰۰ ورودی/کوپن نامعتبر، ۴۰۱ نشست نامعتبر، ۴۰۳ مجوز، ۴۰۴ مرجع ناموجود، ۴۰۹ نسخه/quote/اعتبار/موجودی تغییرکرده؛ همه داده‌های شخصی `no-store`.

در پنل، کوپن خارج workspace عمومی و کش Redis است. کد تکراری بدون حساسیت حروف رد می‌شود. از عدد اعشاری شناور برای محاسبه مالی استفاده نمی‌شود؛ درصد ورودی حداکثر دو اعشار دارد. زمان پنل صریحاً با تقویم میلادی و ساعت دستگاه وارد و UTC ذخیره می‌شود.

## گروه نمایشی گارانتی

`AttributeDefinition.groups` شامل id پایدار، نام، اعضای واقعی و active است. نگاشت مستقل با `attribute.groups.set` و version و idempotency یا همراه ویرایش کامل خصوصیت انجام می‌شود؛ فرمان مستقل فقط گروه‌ها را عوض می‌کند و حتی برای تعریف واردشده با بیش از۱۰۰گزینه، schema واقعی را بازنویسی نمی‌کند؛ روی تمام دسته‌های استفاده‌کننده اثر دارد. گروه ناشناخته، عضو تکراری و عضویت هم‌زمان در دو گروه فعال رد می‌شود. تعریف/حذف گروه، تنوع، موجودی و سفارش قبلی را تغییر نمی‌دهد.

PDP فقط گروه‌های دارای مقدار در همان محصول را نشان می‌دهد. عضو بدون گروه همان نام واقعی را دارد. `?variant=<real-id>` قبلی انتخاب واقعی را حفظ می‌کند؛ انتخاب چیپ گروهی `group=1` resolver ارزان‌ترین عرضه همان ترکیب را فعال می‌کند. انتخاب فروشنده با offer و variant واقعی ادامه می‌یابد؛ API افزودن، تطبیق دقیق آن دو را دوباره کنترل می‌کند. گروه خالی یا ترکیب تعریف‌نشده خرید نمی‌سازد؛ گروه فقط ناموجود مطابق رفتار ناموجود قبلی است.

نگاشت در projection عمومی کاتالوگ هست؛ ویرایش آن نسخه dependency کش را عوض می‌کند. schema کش به v6 رفته تا پاسخ قدیمیِ فاقد این فیلدها از Redis خوانده نشود. هیچ داده اعتبار یا کوپن شخصی وارد projection عمومی نمی‌شود.
