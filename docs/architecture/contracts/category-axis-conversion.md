# تبدیل محورهای تنوع

## قواعد تأییدشده

- درخواست مالک در ۲۶ نوامبر ۲۰۲۶، مجوز اجرای #109 است؛ اجرای تبدیل روی داده فعلی محیط، مجوز جداگانه و برنامه مشخص همان تبدیل می‌خواهد.
- هر تنوع ترکیب یکتا داشته باشد؛ برخورد چندبه‌یک مسدود است. قیمت، موجودی، گارانتی و عرضه‌ها ادغام نمی‌شوند.
- رزرو خرید فعال مانع apply است؛ باید به روال عادی منقضی یا لغو شود و preview تازه گرفته شود.
- سبد و پیش‌فاکتور قدیمی نیاز به بازبینی مشتری دارند. سفارش و دفتر گذشته بازنویسی نمی‌شوند.

## طراحی اجرایی

1. `source`: فقط خواندن دسته، خصوصیات انتخابی کتابخانه، محصول‌ها، تنوع‌ها و نگاشت فعلی؛ بدون شناسه/اطلاعات مشتری.
2. `preview`: دریافت مجموعه محور مقصد و مقدار صریح هر محور برای **تمام** تنوع‌های دسته. هیچ نوشتنی ندارد. مقدار تازه حدس زده نمی‌شود. برخورد، مقدار ناقص/نامعتبر و رزرو گزارش می‌شود.
3. `prepare`: فقط با fingerprint منطبق و preview بدون برخورد، برنامه actor-bound با مهلت فنی ۱۵ دقیقه ذخیره می‌شود. این مهلت ارتباطی با رزرو ۳۰دقیقه‌ای خرید ندارد.
4. `apply`: تأیید صریح شناسه برنامه و fingerprint؛ کنترل مجدد مجوز `category.axes.convert` و نسخه/نگاشت/قیمت/موجودی/رزرو/سبد/quote مرتبط در یک تراکنش مخزن. برنامه مصرف‌شده قابل اجرای دوباره نیست و retry همان برنامه رسید قبلی را برمی‌گرداند.

شناسه تنوع، SKU، رسانه و تمام عرضه‌ها حفظ می‌شوند. snapshot تنوع‌های پیشین در سابقه خصوصی تبدیل نگهداری می‌شود. فقط مقدار محور و نسخه تنوع و نسخه مجموعه تنوع محصول و نسخه دسته تغییر می‌کند. خصوصیت غیرمحور، نقش کارت/فیلتر و توضیحات محصول حذف نمی‌شوند. حذف محور یعنی خاموش‌شدن نقش axis، نه حذف تعریف مشترک یا داده محتوایی محصول.

سبدهای متاثر علامت بازبینی می‌گیرند؛ کم/زیادکردن تعداد جای رضایت به تغییر تنوع را نمی‌گیرد. تأیید مستقل مشتری، پس از دیدن انتخاب جدید، لازم است. previewهای خرید بدون سفارش منقضی می‌شوند؛ snapshot و مبلغ quote سفارش‌های قدیمی ثابت می‌مانند و مسیر بازبینی خرید، پیش‌فاکتور تازه می‌سازد.

## اندازه تراکنش و محدودیت

snapshot خواندنی فعلی شامل ۳۵۳۴ محصول و ۵۰۲۹ تنوع است؛ بزرگ‌ترین دسته ۱۸۹ محصول و بزرگ‌ترین تعداد تنوع یک دسته ۳۰۱ است. برای اجرای نخست سقف فنی **۱۰۰۰ محصول، ۱۰۰۰۰ تنوع و بدنه ۸MiB** در هر تبدیل انتخاب شده است؛ عبور از سقف رد می‌شود و دسته بزرگ نیازمند طرح جداگانه است. این اعداد آزمون کارایی تولید نیستند.

مخزن فعلی کل workspace را با قفل تراکنشی می‌نویسد؛ تبدیل یک دسته در همان تراکنش انجام می‌شود و batch نیمه‌منتشر وجود ندارد. در PostgreSQL خطای ذخیره باید کل تراکنش را rollback کند. زمان قفل روی سخت‌افزار تولید هنوز سنجیده نشده است.

## حریم داده و دامنه

مجوز تبدیل مستقل و قابل انتساب است؛ پیش‌فرض فقط ادمین. برنامه و snapshot خصوصی وارد workspace عمومی، projection و Redis عمومی نمی‌شوند. گزارش اثر فقط تعداد سبد/quote را نمایش می‌دهد. انتقال نقش، تغییر تعریف مشترک enum یا ادغام تنوع در دامنه این قابلیت نیست.

## API و خطاهای نسخه فعلی

- `GET /backoffice/categories/{id}/axis-conversion`: مبدأ فقط‌خواندنی با aliasهای chr برای خصوصیت و تنوع.
- `POST /backoffice/axis-conversions/preview`: `{input:{category_id,version,axis_ids,mapping:[{variant_id,values:[{attribute_id,value}]}]}}`؛ ready، fingerprint، تعداد اثرها و conflictهای مشخص؛ بدون ثبت audit یا plan.
- `POST /backoffice/axis-conversions/prepare`: همان input به همراه fingerprint و هدر Idempotency-Key؛ plan_id در فیلد id، مهلت و اثر ثبت‌شده.
- `POST /backoffice/axis-conversions/apply`: `{plan_id,fingerprint,confirm:true}`؛ رسید ثابت با زمان/اثر اجرای نخست. تأیید false یا حذف‌شده قابل اجرا نیست.

همه مسیرها فقط بک‌آفیس و no-store هستند. مجوز مستقل تبدیل لازم است؛ `workspace.read` برای پوسته پنل مانند فرم‌های موجود لازم می‌ماند. ورودی/مرجع اشتباه۴۰۰، مجوز۴۰۳، مبدأ یا برنامه ناموجود۴۰۴، نسخه/fingerprint نامنطبق یا برنامه منقضی۴۰۹ و خرابی ذخیره۵۰۳ است. رد شدن برنامه draft را از بین نمی‌برد؛ بازخوانی مبدأ در UI یک اقدام صریح است.

`POST /storefront/cart` با action=review و review_variant_version به همراه offer_id و version سبد، انتخاب نمایش‌داده‌شده را تأیید می‌کند. checkout پیش از این اقدام، اقلام علامت‌خورده را نمی‌پذیرد. نسخه تنوع نامنطبق اجازه تأیید انتخاب ندیده را نمی‌دهد.
