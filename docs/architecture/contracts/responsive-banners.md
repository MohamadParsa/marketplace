# بنر دسکتاپ و موبایل

## هدف و طرف‌ها

مالک با درخواست اجرای #7، این برش را طبق [ADR-006](../../decisions/adr-006-responsive-banner-activation.md) فعال کرد. بک‌آفیس همان فرم نوع‌دار بنر را برای دو تصویر و متن/لینک به کار می‌برد. نسخه عمومی فقط با انتشار صریح تغییر می‌کند. صفحه‌ساز، ریل دستی #8، sticky #9، زمان‌بندی و زیرسایت‌ها در این برش نیستند؛ خانه ثابت خودکار به این داده متصل نشده است.

مرجع schema اجرایی: [مدل Go](../../../apps/api/internal/domain/content/banner.go)، [use case بنر](../../../apps/api/internal/application/backoffice/banners.go)، [Command/Audit](../../../apps/api/internal/application/backoffice/model.go) و [نوع‌های وب](../../../apps/backoffice-web/src/shared/types.ts). جدول‌ها رفتار این schema را شرح می‌دهند و مرجع موازی مستقل نیستند.

## داده و رسانه

- Banner: `id,name,version,draft,published?`. نوع این برش فقط بنر است؛ JSON/کد widget دلخواه دریافت نمی‌شود. ترتیب فهرست، ترتیب ایجاد است و این کار ویرایش ترتیب Page نیست.
- Config: `desktop_id,mobile_id,alt,link,enabled`. آدرس فایل دلخواه پذیرفته نیست؛ شناسه‌های تصویر فقط از upload/remove همین بنر تغییر می‌کنند.
- Published: کپی Config و `revision` مستقل. آپلود/حذف فایل، تغییر متن/لینک و فعال/غیرفعال‌کردن draft تا publish روی آن اثر ندارند.
- فایل باینری در repository حافظه‌ای آزمون است. در list و Workspace عمومی داده خام فایل ارسال نمی‌شود؛ restart همه بنرها را بازنشانی می‌کند.

سیاست فنی آزمون، مستقل از سیاست آیکن #4 است: PNG/JPEG/WebP واقعی تا۵MiB؛ هر ضلع۱ تا۴۰۹۶ و مجموع پیکسل حداکثر۸٬۳۸۸٬۶۰۸. سرور قالب/ابعاد را قبل از decode کامل بررسی و نتیجه را PNG بازتولید می‌کند؛ نام/metadata/محتوای اضافی ورودی حفظ نمی‌شوند. خروجی PNG ممکن است از ورودی بزرگ‌تر شود ولی تعداد پیکسل محدود است. SVG/GIF، فایل جعلی/ناقص، بزرگ یا خارج ابعاد رد می‌شوند. normalizer مشترک، محدودیت قبلی آیکن۱MiB/۱۰۲۴ را تغییر نداده است.

نسبت تصویر حفظ می‌شود؛ crop اجباری نداریم. پیشنهاد رابط برای دسکتاپ۱۴۴۰×۴۸۰ و برای موبایل۷۵۰×۹۰۰ است؛ اندازه دقیق الزام نیست. برای اثبات responsive، fixtureهای مستقل۱۴۴۰×۴۸۰ و۶۰۰×۸۰۰ به کار رفته‌اند. نقطه انتخاب فنی آزمون: موبایل تا۷۶۷px و دسکتاپ از۷۶۸px با `picture/source`؛ این breakpoint انتخاب نهایی تولید نیست.

## عملیات و دسترسی

| روش/مسیر | نتیجه و مجوز |
| --- | --- |
| `GET /backoffice/banners` | نشست بک‌آفیس؛ فهرست draft/published، policy و can_edit؛ مدیرکل/عملیات ویرایش، سایر نقش‌های پنل فقط مشاهده |
| `POST /backoffice/commands` | actionهای جدول بعد، همراه version و idempotency_key؛ کاربر و نقش جاری در تراکنش دوباره کنترل می‌شوند |
| `POST /backoffice/banners/{id}/media/{desktop|mobile}` | multipart فقط file/version/idempotency_key؛ مدیرکل/عملیات؛ نتیجه `{asset_id,version}` متعلق به همان عملیات |
| `GET /backoffice/banner-media/{id}` | فایل draft یا published با احراز پنل؛ فروشنده یا مهمان دسترسی ندارند |
| `GET /content/banners` | عمومی؛ فقط snapshot منتشرشده و enabled؛ draft، باینری و version داخلی ویرایش نشت نمی‌کنند |
| `GET /content/banner-media/{id}` | فقط فایل متصل به snapshot منتشرشده و فعال؛ فایل draft/بدون اتصال/نسخه غیرفعال404 |
| `GET /content/banners/{id}/view` | نمایش HTML مستقل نسخه منتشرشده برای بررسی۳۹۰/۱۴۴۰، با picture، alt و لینک معتبر؛ صفحه اصلی مشتری نیست |

پاسخ‌ها `no-store` دارند. مسیرهای خصوصی و viewer HTML، `X-Robots-Tag: noindex, nofollow` دارند؛ HTML نیز meta robots و CSP محدود دارد. فایل‌ها PNG با nosniff هستند. لینک داخلی در همان تب باز می‌شود و قالب HTML متن/عنوان را escape می‌کند.

| action | ورودی / رفتار |
| --- | --- |
| `banner.create` | name؛ ساخت draft خالی با version۱؛ اسم غیرخالی تا۸۰ نویسه در سقف قبلی۱۶۰ بایت نام Command |
| `banner.save` | target، version و Config کامل؛ فقط متن/لینک/enabled تغییر می‌کنند؛ شناسه‌های رسانه باید همان draft جاری باشند |
| `banner.media.remove` | target، version و value از desktop/mobile؛ حذف مرجع draft، بدون تغییر snapshot عمومی |
| `banner.publish` | target و version؛ هر دو فایل واقعی و قابل decode، alt غیرخالی و لینک معتبر لازم؛ کپی اتمیک Config به Published و افزایش revision |

در برش آزمون، لینک خالی یا مسیر داخلی مانند `/products/sample` مجاز است؛ scheme، `//`، backslash، فاصله/کنترل و شکل percent-encoded خطرناک رد می‌شوند. لینک خارجی نیاز این برش نیست. alt در draft می‌تواند خالی باشد ولی انتشار به alt غیرخالی تا۲۰۰ نویسه نیاز دارد. فعال‌سازی عمومی حتی برای snapshot غیرفعال هم از همان اعتبارسنجی می‌گذرد.

## نسخه، خطا و تکرار

هر تغییر موفق draft/تصویر/انتشار version را یک واحد بالا می‌برد. publication revision فقط با publish بالا می‌رود. version کهنه409 و تغییر نامعتبر400 است؛ درخواست‌های هم‌زمان روی یک نسخه فقط یک برنده دارند. audit و تصویر/config/publication در تراکنش واحد ثبت می‌شوند.

کلید یکسان با actor/فرمان/بدنه یکسان اثر دوم ندارد؛ بدنه متفاوت409 است. رسید upload، asset_id و version **عملیات اولیه** را در retry برمی‌گرداند، نه نسخه تازه‌تر دیگران؛ بنابراین retry به شکل پنهان اجازه overwrite نسخه تازه را نمی‌سازد. پس از لغو مجوز، retry نیز رد می‌شود.

در جایگزینی رسانه، فایل عمومی قبلی تا انتشار بعدی حفظ می‌شود. فایل‌هایی که دیگر در هیچ draft یا published مرجع ندارند جمع‌آوری می‌شوند. انتشار نامعتبر، public قبلی را تغییر نمی‌دهد. غیرفعال‌کردن draft تا انتشار بنر را پنهان نمی‌کند؛ انتشار غیرفعال آن را از پاسخ عمومی و مجوز دریافت فایل خارج می‌کند.

| HTTP | معنا / رفتار رابط |
| --- | --- |
| 400 | فایل/لینک/Config نامعتبر یا رسانه ناقص؛ مقدار ثبت‌شده و پیش‌نمایش معتبر قبلی حفظ شود |
| 401/403 | نشست یا مجوز نامعتبر؛ تغییر اعمال نشود |
| 404 | مرجع یا فایل قابل مشاهده پیدا نشد؛ draft عمومی نشود |
| 409 | نسخه/کلید متعارض؛ متن و لینک کاربر نگه داشته و بازخوانی/بازبینی لازم شود |
| 413 | حجم بالاتر از سیاست؛ فایل کوچک‌تر انتخاب شود |

## رابط و پذیرش

دو جایگاه مستقل انتخاب/پیش‌نمایش/ثبت/حذف تصویر وجود دارند. انتخاب محلی و انصراف، upload نمی‌کنند. ثبت تصویر فقط draft را تغییر می‌دهد. انتشار با تغییر ثبت‌نشده، فایل در حال بررسی/ثبت، تصویر ناقص یا alt خالی در رابط غیرفعال است؛ سرور مستقل کنترل می‌کند. پیام نتیجه در خود فرم قرار می‌گیرد و دکمه‌های فرم را نمی‌پوشاند. تصاویر محلی/خصوصی از object URL با cleanup استفاده می‌کنند.

معیارهای CV-R2-07-AC01/02 در [BDD](../../bdd/features/experiences/responsive-banners.feature) و [گزارش اجرا و تصاویر](../../delivery/review-v1-1/issue-7-verification.md) پیوند دارند. storage واقعی، CDN، انتشار خودکار و اتصال خانه مشتری از موفقیت این برش نتیجه نمی‌شوند.


## حالت داده‌محور چهار ریل — اصلاح #41، ۲۰۲۶-۱۱-۲۳

`BannerConfig.catalog_category_id` اختیاری و فقط برای placement=promo و دسته منتشر یکی از چهار ریل معتبر است. تصویر و مقصد از محصول موجود همان ریل در خانه ساخته می‌شود؛ در نبود محصول پنهان است. این حالت به فایل ثابت desktop/mobile نیاز ندارد؛ تصویر ثابت همان الزامات قبلی را دارد. انتخاب منبع در پنل با دکمه است و preview داده‌محور از همان خانه استفاده می‌کند. [دلیل، شاهد و تصاویر](../../delivery/storefront-followups/issue-41-verification.md). این اصلاح CMS عمومی یا ریل دستی #8 را فعال نمی‌کند.
