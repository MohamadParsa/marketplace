# قرارداد نسخه بررسی بک‌آفیس

## هدف و طرف‌ها

رابط بک‌آفیس React و API مشترک Go برای بررسی با داده ساختگی. این قرارداد مجوز عملیات بانکی، پیامک واقعی یا نگهداری داده عملیاتی نیست. schema پاسخ در `apps/api/internal/application/backoffice/model.go` و انواع رابط در `apps/backoffice-web/src/shared/types.ts` نگهداری می‌شوند؛ تولید خودکار client هنوز انجام نشده و از محدودیت‌های این نسخه است.

## عملیات و دسترسی

| روش و مسیر | کاربرد | دسترسی |
| --- | --- | --- |
| `POST /backoffice/auth/request-otp` | درخواست OTP آزمون | شماره کاربر موجود |
| `POST /backoffice/auth/verify-otp` | ایجاد نشست | کد معتبر و حساب فعال |
| `POST /backoffice/auth/logout` | ابطال نشست | Bearer token |
| `GET /backoffice/workspace` | نمای یکپارچه صفحات آزمون | نقش پایه بک‌آفیس یا مجوز `workspace.read`؛ کاربران و رجیستری فقط برای ادمین، اطلاعات مالی فقط برای ادمین، finance یا `finance.read` |
| `POST /backoffice/commands` | اجرای فرمان با ثبت audit | طبق مجوز هر فرمان |

در هر درخواست، فعال‌بودن و نقش جاری حساب از repository خوانده می‌شود؛ تغییر نقش یا غیرفعال‌سازی فقط مخفی‌کردن منو نیست. فروشنده حق استفاده از این endpointها را ندارد.

## فرمان‌ها

- `user.create / user.toggle / user.role`: فقط admin؛ برای اعطای admin احراز مجدد لازم است. [قرارداد اختیار ادمین](#مدیریت-اختیار-ادمین) را ببینید.
- `store.create / store.toggle / category.create / category.archive / product.publish / product.reject / shipping.update`: super-admin و operations.
- `case.start / case.close / case.refund / case.assign / order.deliver`: super-admin و support.
- `transfer.resolve`: super-admin و finance.
- `rule.toggle / notification.retry`: super-admin.

مجوز سفارشی هر فرمان می‌تواند علاوه بر نقش‌های پایه اختیار همان فرمان را بدهد. رجیستری سفارشی اجازه تعریف فرمان‌های مدیریت حساب، عضویت، نقش یا اعطای ادمین را نمی‌دهد.

بدنه فرمان شامل `action`، `target` و `idempotency_key` و ورودی لازم همان فرمان است. `version` برای محصول، سفارش، پرونده و انتقال مالی لازم است. درخواست مجدد با کلید و بدنه یکسان اثر دوباره ندارد؛ استفاده از همان کلید با بدنه متفاوت conflict است. کل تغییر و audit اتمیک اعمال می‌شوند. بدنه حداکثر ۱۶KB است و فیلد ناشناخته رد می‌شود.

## خطاها

| HTTP | معنا | رفتار رابط |
| --- | --- | --- |
| 400 | ورودی نامعتبر | نمایش خطای فرم |
| 401 | نشست نامعتبر، منقضی یا حساب غیرفعال | خروج و پاک‌سازی query cache |
| 403 | فقدان مجوز | عدم اعمال تغییر |
| 404 | مرجع ناموجود | نمایش خطا |
| 409 | نسخه کهنه یا وضعیت نامعتبر | دریافت مجدد داده و بررسی عملیات |
| 429 | محدودیت OTP | تلاش پس از مهلت |
| 500 | خطای داخلی | پیام عمومی؛ جزئیات داخلی در response نیست |

## قواعد داده و سازگاری

مبلغ API ریال صحیح است؛ نمایش رابط تومان است. زمان ISO 8601 و نمایش با تقویم فارسی و منطقه `Asia/Tehran` انجام می‌شود. پاسخ خصوصی `no-store` است و token فقط در حافظه مرورگر نگهداری می‌شود. داده آزمون محدود است و این endpoint هنوز pagination ندارد؛ برای محیط عملیاتی به قرارداد صفحه‌بندی و query اختصاصی نیاز است.

## مدیریت اختیار ادمین

`admin` عنوان نقش فعلی `super-admin` است. در ساخت کاربر و تغییر نقش، API هر دو مقدار را می‌پذیرد و پاسخ‌های نسخه آزمون برای سازگاری همچنان `super-admin` می‌دهند. ادمین می‌تواند نقش‌های موجود را تعیین کند؛ ایجاد، ارتقا یا فعال‌سازی دوباره حساب ادمین به احراز مجدد نیاز دارد. غیرفعال‌سازی یا تنزل آخرین ادمین فعال با ۴۰۹ رد می‌شود.

۱. `POST /backoffice/auth/request-admin-otp` با نشست فعلی ادمین، کد را برای حساب خود او درخواست می‌کند و ۲۰۲ با `request_id` می‌دهد. کد آزمون فقط در `local/test` در پاسخ دیده می‌شود.
۲. همان نشست، فرمان `POST /backoffice/commands` را با `reauthentication: {"request_id":"…","code":"…"}` می‌فرستد. این کد ۹۰ ثانیه اعتبار دارد؛ به همان نشست وابسته است، با ورود عادی قابل جابه‌جایی نیست و برای تغییر دوم قابل استفاده نیست. خطاهای ۴۰۳ `reauthentication_required` و `invalid_reauthentication` به‌ترتیب نبود تأیید و تأیید نامعتبر را نشان می‌دهند.
۳. تغییر نقش یا وضعیت حساب، نشست قبلی بک‌آفیس آن کاربر را بی‌اعتبار می‌کند. از اولین درخواست بعدی به API باید دوباره با نقش جاری وارد شود. سابقه تغییر برای ادمین، شامل عامل، هدف، زمان، نقش قبل و نقش جدید است؛ کد و درخواست احراز مجدد در سابقه ثبت نمی‌شوند.

## نقش سفارشی و عضویت

ادمین رجیستری، نقش‌ها، انتساب‌ها و عضویت‌ها را در `workspace.access` دریافت می‌کند و در صفحه کاربران مدیریت می‌کند. نقش‌های `global` و `store` رجیستری مجوز جدا دارند. قاعده جمع مجوز برای هر فروشگاه مستقل اعمال می‌شود و عضویت به‌تنهایی مجوز ایجاد نمی‌کند.

| فرمان | ورودی و قاعده |
| --- | --- |
| `role.create / role.update / role.delete` | نام، `scope` و `permissions` برای تعریف؛ تغییر و حذف با شناسه و `version`. نقش دارای انتساب حذف نمی‌شود؛ ابتدا انتساب‌ها لغو شوند. |
| `membership.add / membership.remove` | `target` شناسه کاربر و `store_id`. لغو عضویت، تمام نقش‌های همان کاربر در همان فروشگاه را لغو می‌کند. |
| `user.role-grant / user.role-revoke` | `target` شناسه کاربر، `value` شناسه نقش؛ نقش فروشگاه به `store_id` و عضویت موجود نیاز دارد. نقش سراسری `store_id` نمی‌پذیرد. |

تغییر مجوزهای سراسری، نشست قبلی بک‌آفیس کاربر متأثر را بی‌اعتبار می‌کند. مجوز فروشگاه از داده جاری در هر درخواست خوانده می‌شود.

## برش آزمون هویت و اختیار فروشگاه

[CV-R2-01](../../delivery/review-v1-1/tasks/cv-r2-01-single-user.md) در `local/test` با داده حافظه‌ای یا PostgreSQL مجزا قابل بررسی است. حساب ساختگی `09000000002` در بک‌آفیس، فروشنده و API آزمایشی مشتری یک `User.ID` دارد؛ نشست هر محیط در همان محیط معتبر است. ورود فروشنده `user.StoreIDs` و مجوز هر فروشگاه را برای نمایش کنترل‌ها برمی‌گرداند؛ سرور مجوز را از داده جاری بررسی می‌کند.

| مسیر API آزمون | مجوز و نتیجه |
| --- | --- |
| `GET /seller/stores/{storeID}/offers` | عضویت و مجوز مشاهده در همان فروشگاه؛ پاسخ فقط عرضه‌های همان فروشگاه است. |
| `PUT /seller/stores/{storeID}/offers/{offerID}/stock` | عضویت و مجوز ویرایش موجودی در همان فروشگاه؛ بدنه `{"stock":9,"version":0}`؛ نتیجه موفق ۲۰۴، نسخه کهنه ۴۰۹، شناسه عرضه خارج از فروشگاه ۴۰۴ و نبود مجوز ۴۰۳. |
| `POST /storefront/auth/request-otp` و `verify-otp` | ورود آزمایشی مشتری با شماره حساب موجود؛ بدون ساخت حساب دوم. |
| `GET /storefront/account/profile` و `/storefront/account/purchases` | فقط نشست مشتری؛ پروفایل و خریدهای ساختگی از شناسه همان نشست خوانده می‌شوند. خرید یا پرداخت ایجاد نمی‌شود. |

حساب بالا می‌تواند موجودی `s1` را ویرایش کند و `s2` را فقط ببیند. حساب ساختگی `09120000002` عضو دوم `s1` است و فقط می‌تواند عرضه‌های آن را ببیند. پروفایل و مالکیت خرید ساختگی `BUY-501` به شناسه همان حساب اول وصل‌اند. اتصال سایت و پرداخت واقعی در گیت مرحله بعدند.

### اجرای نسخه پایدار آزمون

برای PostgreSQL ۱۵ یا جدیدتر و یک پایگاه خالی و جدا، `APP_ENV=test` و `REVIEW_DATABASE_URL` را تنظیم کنید. از `apps/api` نخست `go run ./cmd/migrate up` و سپس `go run ./cmd/api` را اجرا کنید. migration نسخه آزمون در [db/migrations](../../../db/migrations) است، با قفل تراکنشی اجرا می‌شود و اجرای دوباره آن بی‌اثر است. داده ساختگی فقط بار اول ثبت می‌شود. کاربر، نقش، عضویت، انتساب و مالکیت خرید با قیود رابطه‌ای ذخیره می‌شوند و تغییرات آزمون و سابقه هم باقی می‌مانند. نشست و کد یک‌بارمصرف پس از restart از بین می‌روند. بدون این تنظیم، داده در حافظه است. این تنظیم برای انتشار یا داده غیرآزمایشی استفاده نمی‌شود.

## نمونه و پذیرش

حساب‌های کاملاً ساختگی `09000000001` تا `09000000005` به‌ترتیب مدیرکل، عملیات، پشتیبانی، مالی و مشاهده‌گر هستند. کد آزمون فقط در محیط local/test نمایش داده می‌شود.

شواهد اجرا: `apps/api/internal/bootstrap/backoffice_test.go`، `apps/api/internal/application/backoffice/service_test.go` و `tests/e2e/backoffice-smoke.py`.
