## مدل و ماندگاری

[WishlistEntry](../../../apps/api/internal/domain/customer/wishlist.go) شامل user_id/product_id/created_at است؛ رابطه بر **محصول** قرار دارد و رنگ، گارانتی، تنوع یا فروشنده بخشی از کلید نیست. منبع داده خصوصی `Workspace.Wishlist` در payload پایدار PostgreSQL موجود است؛ جدول/سرویس جدید یا migration لازم نبود. حذف محصول از کاتالوگ این ردیف را cascade نمی‌کند تا مشتری بتواند آن را حذف کند.

[Service](../../../apps/api/internal/application/backoffice/wishlist.go) هویت customer را از نشست می‌گیرد و داخل Snapshot/Update دوباره active/access_version را کنترل می‌کند. ثبت در Update سریال repository (قفل FOR UPDATE در PG، mutex در حافظه) یکتایی user/product را برقرار می‌کند. PUT تکراری created_at را تغییر نمی‌دهد و ردیف دوم نمی‌سازد؛ DELETEِ ردیف غایب موفق و بی‌اثر است. حذف فقط ردیف user فعلی را هدف می‌گیرد. پاک‌کردن و ذخیره دوباره، زمان تازه می‌گیرد. ترتیب نزولی created_at و سپس product_id صعودی، در تساوی پایدار است.

خواننده نسخه تازه نبود فیلد wishlist در workspace قدیمی را فهرست خالی می‌داند؛ کاربران/نقش‌ها/سفارش/بانک/دفتر/کاتالوگ قبلی بازنویسی نمی‌شوند. همه writerهای همان workspace باید نسخه سازگار داشته باشند؛ writer قدیمی که فیلد تازه را نمی‌شناسد، گزینه مناسبی برای انتشار هم‌زمان یا rollback نوشتنی نیست. این برش داده را در معماری فعلی نگه می‌دارد و سرویس شخصی جدا معرفی نمی‌کند.

## HTTP و دسترسی

تمام endpointها Bearer با surface=customer می‌خواهند؛ actor از body/query قابل تعیین نیست. آدرس رابط `/account/wishlist` است. body برای PUT/DELETE باید خالی باشد. شناسه مسیر، ID داخلی product برگشتی PDP است؛ URL کارت از ProductURL عمومی chr ساخته می‌شود و از شناسه wishlist برای ساخت URL حدسی استفاده نشود.

| عملیات | ورودی | خروجی |
| --- | --- | --- |
| GET /storefront/account/wishlist | page پیش‌فرض۱؛ page_size پیش‌فرض۲۴، حداکثر۴۸؛ page در۱تا۱۰۰۰۰۰۰ | items، total، page، page_size؛ هر item شامل product_id و product: ListingCard یا null |
| GET /storefront/account/wishlist/{id} | شناسه محصول | product_id، saved، total فقط برای حساب جاری؛ پاسخ درباره وجود عمومی کالا اطلاعاتی نمی‌دهد |
| PUT /storefront/account/wishlist/{id} | بدون body | وضعیت ذخیره و total؛ فقط محصول عمومی طبق قواعد همان PDP قابل افزودن است، حتی اگر فعلاً موجود نباشد |
| DELETE /storefront/account/wishlist/{id} | بدون body | وضعیت ذخیره false و total؛ حذف کالای پنهان/حذف‌شده هم مجاز است |

نام query ناشناخته، چند مقدار برای یک پارامتر، صفحه/اندازه نامعتبر، ID خالی/طول بیش از۱۲۸/اسلش یا body اضافه با۴۰۰ رد می‌شوند. با PUT/DELETE حالت مطلوب صریح است؛ Idempotency-Key جدا لازم نیست و replay وضعیت مطلوب رکورد دوم/حذف کاربر دیگر نمی‌سازد. ترتیب دو فرمان متضاد هم‌زمان ترتیب commit سرور است؛ کلاینت از فرمان موازی برای یک قلب جلوگیری می‌کند.

خطاها:۴۰۱ نشست نامعتبر/سطح اشتباه؛۴۰۳ حساب غیرفعال یا نسخه دسترسی نامعتبر؛۴۰۴ هنگام افزودن محصول غیرعمومی/ناموجود در کاتالوگ؛۴۰۰ ورودی؛۵۰۳ مشکل زیرساخت. ناموجودی stock به معنی۴۰۴ نیست. خطا در حذف یا ذخیره حالت موفق ساختگی نمی‌سازد؛ داده و ورودی قابل بازیابی می‌مانند.

## حریم خصوصی، نمایش و کش

[handler خصوصی](../../../apps/api/internal/transport/http/wishlist_handler.go) همه پاسخ‌ها و خطاهای مسیر را no-store با Vary:Authorization برمی‌گرداند؛ ETag عمومی یا ذخیره Redis ندارد. فهرست با صفحۀ۲۴تایی خوانده می‌شود، نه دریافت همه علاقه‌مندی‌ها در هدر. هدر فقط یک خواندن page_size=1 برای total دارد؛ وضعیت قلب PDP جدا خوانده می‌شود.

کارت‌ها با **همان** publicProduct/listingCard و visibility دسته/اجداد/برند ساخته می‌شوند؛ snapshot قدیمی نام/عکس/قیمت نگه نمی‌داریم که کالای پنهان از آن افشا شود. product:null فقط شناسه قبلاً ذخیره‌شده خود مشتری را برای حذف دارد؛ URL، نام، ویژگی و تصویر پنهان در DTO نیستند. total شامل همین ردیف عمومی غیرقابل‌دسترسی هم هست. قیمت و تصویر محصول عمومی در خواندن تازه از کاتالوگ فعلی می‌آیند؛ علاقه‌مندی رزرو قیمت/موجودی نیست.

Wishlist از پاسخ workspace بک‌آفیس و projection کاتالوگ عمومی خارج است؛ پنل فروشنده نیز whitelist مستقل خود را دارد. این برش صفحه مدیریتی برای دیدن علاقه‌مندی دیگران ایجاد نمی‌کند؛ درخواست فقط قابلیت خصوصی خریدار است. تغییر آن به cache stamp عمومی دست نمی‌زند؛ آزمون PG این جدایی را بررسی می‌کند.

## قرارداد UI و خطا

[Provider](../../../apps/storefront-web/src/wishlist.tsx) در محدوده نشست حافظه‌ای همان حساب است؛ با logout/تعویض حساب، context و children با کلید نشست تازه ایجاد می‌شوند تا ردیف/قلب/شمارنده قبلی در حساب بعدی نماند. پاسخ خلاصه قدیمی نمی‌تواند شمارنده موفق mutation را بازنویسی کند. هیچ فهرست یا token تازه‌ای در localStorage ذخیره نمی‌شود؛ احراز هویت از همان CommerceProvider است.

قلب PDP طبق اصلاح صریح مالک فقط icon خالی/پُر، بدون متن/کادر/پس‌زمینه است؛ aria-pressed/label/tooltip/focus و حداقل touch target۴۴پیکسل دارد؛ از BusyRegion/overlay مشترک استفاده می‌کند. مهمان به `/login?return=<current PDP>` می‌رود؛ پس از ورود به همان PDP برمی‌گردد و می‌تواند ذخیره کند. صفحه علاقه‌مندی از همان ProductCard خانه/PLP، رنگ primary چریوا و طرح A استفاده می‌کند؛ آیکن هدر و لینک در پروفایل هر دو به آن می‌رسند. روی کارت صفحه شخصی دکمه حذف مستقل است و داخل لینک محصول قرار ندارد.

فهرست حالت loading، خطا/تلاش مجدد، empty، کالای غیرقابل‌دسترسی، ناموجود، موبایل و صفحه‌بندی دارد. حذف آخرین ردیف صفحه بعدی، به آخرین صفحه معتبر برمی‌گردد. پاسخ دیررس پس از تغییر حساب/صفحه یا unmount اعمال نمی‌شود. صفحه خصوصی با CommerceShell موجود noindex/nofollow می‌گیرد.
