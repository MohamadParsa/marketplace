## مدل و سازگاری اجرایی

مرجع schema: [User/Command](../../../apps/api/internal/application/backoffice/model.go)، [مدل identity](../../../apps/api/internal/domain/identity/model.go) و [UserInput/Directory/Filter](../../../apps/api/internal/application/backoffice/users_management.go).

migration افزایشی [000012](../../../db/migrations/000012-user-management.up.sql) ستون‌های `first_name,last_name,gender,version,password_change_required` را با پیش‌فرض خالی/صفر/false اضافه می‌کند؛ هیچ نام، هش رمز یا داده مالی backfill/جایگزین نمی‌شود. نسخه کاربر قدیمی صفر معتبر است. اجرای down فقط در schema آزمون بررسی شده و عملیات لازم انتشار نیست.

جنسیت در نسخه جاری `""/female/male`؛ نام/نام خانوادگی هرکدام تا۱۶۰بایت و فعلاً اختیاری‌اند، موبایل معتبر الزامی، ایمیل تا۲۵۴بایت و نرمال‌شده است. نام نمایشی با نام‌های جدیدِ غیرخالی ساخته می‌شود؛ اگر هر دو خالی باشند نام قبلی حفظ می‌شود. ویرایش پروفایل شخصیِ قدیمی همچنان display name را می‌پذیرد و نام/نام خانوادگی را با حدس بازنویسی نمی‌کند.

## API فهرست، ذخیره و خروجی

همه مسیرها خصوصی، `no-store` و JSON هستند. فیلترهای حاوی نام/موبایل/ایمیل در **بدنه POST** هستند، نه URL.

| مسیر | دسترسی و معنا |
| --- | --- |
| `POST /backoffice/users/query` | `users.read`؛ مالی/دارنده مجوز قبلی شارژ کیف پول، دسترسی خواندن قبلی خود را حفظ می‌کند. بدنه `{filter:{...}}`، خروجی rows,total,page,size و قابلیت‌های ویرایش/رمز/انتساب |
| `POST /backoffice/users/save` | `users.write`؛ رمز غیرخالی علاوه بر آن `users.password.reset` می‌خواهد. بدنه UserInput، هدر Idempotency-Key، پاسخ ردیف مجاز کاربر |
| `POST /backoffice/users/export` | `users.read` و `grid.export`؛ بدنه `{filter:{...},ids:[...]}`؛ ids خالی یعنی تمام نتیجه فیلتر، وگرنه اشتراک انتخاب‌ها با همان فیلتر؛ سقف۱۰هزار |

فیلترها: نام، نام خانوادگی، موبایل، ایمیل به‌صورت contains نرمال‌شده؛ برای نام قدیمیِ فاقد فیلد جدا، جست‌وجوی نام روی display name است. وضعیت true/false، جنسیت، نقش پایه/سفارشی و عضویت فروشگاه ترکیب AND دارند. مرتب‌سازی نام صعودی/نزولی یا شناسه، tie با ID؛ page از۰ و size حداکثر۱۰۰، پیش‌فرض۲۰. export تمام صفحات را می‌دهد، نه صرفاً صفحه بارگیری‌شده.

فرم جدید از query جدا استفاده می‌کند؛ پوسته با `GET /backoffice/workspace?user_directory=separate` دیگر فهرست کامل کاربران را دریافت نمی‌کند. رفتار GET قدیمی برای consumerهای قبلی حفظ شده است. فیلتر/paging در سرویس سرور روی identity snapshot انجام می‌شود؛ هنوز query ایندکس‌دار SQL برای صفحه‌بندی کاربران ساخته نشده و خواندن داخلی snapshot هویت باقی است. این با ادعای pagination در SQL یا حذف کل workspace پنل یکسان نیست.

مجوز و actor در تراکنش دوباره بررسی می‌شوند. کاربر دارای مجوز ویرایشِ تفویض‌شده نمی‌تواند حساب کارکنان دارای نقش پایه یا grant سراسری را تغییر دهد؛ این کار فقط برای admin است. فعال/غیرفعال مستقل از نقش است. `version` و `active` در ورودی ذخیره باید صریح باشند؛ فعال‌سازی ادمین غیرفعال از save عادی رد و از اکشن تأییدشده user.toggle انجام می‌شود. تغییر موبایل موجود، فیلد ناشناخته و تزریق مجوز رد می‌شوند.

رمز فقط bcrypt می‌شود. برای retry، fingerprint شامل رمز نیست؛ بررسی درخواست تکراریِ دارای رمز با bcrypt خصوصی انجام می‌شود. شواهد retry در JSON خصوصی workspace نگهداری و از خروجی workspace، کاتالوگ و گرید حذف می‌شوند. هیچ رمز خام، هش رمز، کد ملی یا داده بانکی در DTO فهرست/فایل Excel نیست. نمونه رمز واقعی در برنامه تعریف نشده است.

## رمز موقت و نشست محدود

پاسخ ورود در هر سه surface، `user.PasswordChangeRequired` را برمی‌گرداند. در این وضعیت token صادر می‌شود ولی `Authenticate` عادی آن را رد می‌کند؛ ورود به workspace، پروفایل، سبد، سفارش، مالی و مجوزهای فروشگاه مجاز نیست. فقط خروج و مسیر زیر قابل استفاده‌اند:

`POST /{backoffice|seller|storefront}/auth/complete-password` با token محدود و `{password:...}`.

رمز جدید باید با رمز موقت متفاوت و طبق سیاست فعلی۸تا۷۲بایت باشد. سرور فعال‌بودن/نسخه دسترسی/الزام تغییر را اتمیک بررسی، hash را عوض، flag را پاک و epoch نشست را زیاد می‌کند؛ token محدود باطل و token عادی جدید برمی‌گردد. نگه‌داشتن token در UI تا این مرحله فقط حافظه‌ای است. کلیک بازگشت، دسترسی عادی ایجاد نمی‌کند.

بازنشانی قدیمی ادمین هم همین سیاست موقت و لاگ metadata را رعایت می‌کند و اختیار جاری ادمین را در تراکنش بازبینی می‌کند. بازیابی معتبر OTP مالک می‌تواند رمز شخصی را تعیین کند. تغییر رمز شخصی، نشست جاری را با نسخه تازه نگه می‌دارد و سایر نشست‌های قبلی را نامعتبر می‌کند؛ ویرایش پروفایل با epoch قدیمی هم در تراکنش رد می‌شود.

## نقش و عضویت

CRUD نقش و `user.role`, `user.role-grant/revoke`, `membership.add/remove` همان `/backoffice/commands` موجودند؛ موتور موازی ساخته نشده است. نقش سفارشی فقط مجوزهای allowlist registry همان scope را می‌پذیرد. نام/دامنه/نسخه نقش و استفاده‌شدن آن در سرور کنترل می‌شوند؛ scope نقش موجود قابل تغییر نیست.

UI در تغییر انتساب، `user_version` و در grant تازه `role_version` را می‌فرستد تا تغییر هم‌زمان کاربر یا تعریف نقش بی‌صدا اعمال نشود. این فیلدها برای consumer قدیمی اختیاری‌اند؛ فرم جدید همیشه آن‌ها را می‌فرستد. حذف عضویت، grantهای همان فروشگاه را هم حذف می‌کند و پیش از آن تأیید UI می‌گیرد. انتساب نقش جهانی به store یا نقش store به کاربر غیرعضو رد می‌شود. مجوز مؤثر و نام نقش‌های منبع در هر محدوده جدا نمایش داده می‌شوند؛ نقش‌های پایه نیز با نام مستقل مشخص‌اند.

## خطا و مرز تحویل

۴۰۰ ورودی/رمز/دامنه نامعتبر؛۴۰۱ نشست منقضی/محدود یا فاقد هویت سطح ورود؛۴۰۳ نبود مجوز یا هدف محافظت‌شده؛۴۰۴ کاربر/نقش حذف‌شده؛۴۰۹ نسخه/کلید متعارض، موبایل/ایمیل تکراری، آخرین ادمین یا نقش مصرف‌شده. پیام خاص تماس تکراری و آخرین ادمین در UI هست؛ draft در خطا حفظ و refresh صریح است.

لاگ عملیات فقط actor/action/target/time دارد؛ رمز و محتوای request در لاگ/URL نوشته نمی‌شوند. ممیزی جامع scope فروشنده در #71، تغییر موبایل امن، OTP ایمیلی، سرویس بیرونی و تجدید معماری کل workspace خارج این برش‌اند. هیچ‌یک از این دو Issue به معنای پوش یا استقرار لیارا نیست.
